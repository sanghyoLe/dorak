# 도락 (DORAK)

> 좋은 식당을 찾는 즐거움

도락은 장기적으로 전국 음식점을 포괄하는 한국형 음식점 리뷰·랭킹 플랫폼이다. 단순한 맛집 지도나 리뷰 앱이 아니라 소비자용 탐색 서비스, 신뢰도 높은 음식점 데이터·평점 플랫폼, 점주용 운영 도구를 함께 구축한다.

현재는 개인 프로젝트이므로 서울의 영업 중 일반음식점 데이터를 먼저 연결하고, 리뷰 신뢰도와 정보 최신화 기능을 단계적으로 깊게 만든다. 배포는 월 고정비 0원을 목표로 하는 [비용 우선 운영안](./docs/architecture/COST_FIRST_ARCHITECTURE.md)을 따른다.

## 개발 프리뷰 실행

Node.js 20.9 이상과 pnpm 9.15.9가 필요하다. 저장소 루트에서 다음 명령으로 의존성을 설치하고 단일 Next.js 애플리케이션을 실행한다.

```bash
pnpm install
pnpm dev
```

- 소비자 웹: `http://localhost:3000`
- 운영 화면: `http://localhost:3000/ops`
- API 상태: `http://localhost:3000/api/health`

기본 로컬 인프라는 PostgreSQL 하나다.

```bash
docker compose -f infra/compose.yaml up -d postgres
DATABASE_URL=postgres://dorak:dorak_local_only@localhost:5432/dorak pnpm db:migrate
DATABASE_URL=postgres://dorak:dorak_local_only@localhost:5432/dorak pnpm db:seed
DATABASE_URL=postgres://dorak:dorak_local_only@localhost:5432/dorak pnpm db:smoke
```

품질 검사는 다음 명령으로 실행한다. `visual:test`는 Next.js 애플리케이션을 먼저 실행해야 하며 로컬 Chrome이 필요하다.

```bash
pnpm typecheck
pnpm test
pnpm build
pnpm visual:test
```

실제 서울 공공데이터를 적재한 DB는 [데이터 검증 절차](./docs/architecture/DATA_INGESTION.md)의 `data:verify:seoul`과 `data:verify:http` 명령으로 원장 품질과 공개 API의 목록·상세·검색 흐름을 함께 확인한다.

## 현재 실행 가능한 MVP

현재 코드는 다음 핵심 흐름을 실제 PostgreSQL과 연결해 제공한다.

- 식당명·지역·장르·메뉴 통합 검색과 장르 필터
- 음식점 상세, 공개 리뷰 목록, 평점·리뷰 수 집계
- Google 계정 로그인과 로컬 체험 계정
- 방문일·방문 자기확인을 필수로 하는 리뷰 작성
- 계정당 식당별 리뷰 1건, 계정당 일 5건 제한, 외부 링크 차단
- 계정 확인·방문일 자기입력·근거 확인을 과장 없이 구분하는 표시
- 운영자 전용 식당 후보 검수와 리뷰 숨김, 변경 감사 기록
- 개인정보 처리 안내, 검색엔진 색인 opt-in, 기본 보안 헤더
- PostgreSQL 통합 테스트와 실제 HTTP 흐름을 검사하는 GitHub Actions CI

MVP에는 영수증·예약 기반 방문 인증이 아직 없다. 따라서 사용자가 방문했다고
직접 확인한 리뷰는 `방문일 자기입력`으로만 표시하며 `방문 확인`으로 승격하지
않는다. 예시 식당과 예시 리뷰도 실제 데이터처럼 보이지 않도록 별도 표시한다.

시드 직후 프리뷰의 음식점과 후보는 합성 데이터다. 서울시 CSV를 가져오면 `approved_source` 지점이 PostgreSQL 원장에 추가된다. `DATABASE_URL`이 있으면 Next.js 서버가 PostgreSQL을 사용하고, 없으면 UI 개발용 인메모리 저장소로 실행된다. 인메모리 모드에서는 서버 재시작 시 검수 결정이 초기화된다. 소비자 화면, `/ops`, `/api`는 하나의 배포 단위다.

실제 음식점 데이터와 지도를 연결하려면 [데이터 수집 문서](./docs/architecture/DATA_INGESTION.md)의 CSV 가져오기를 실행하고, `.env.example`의 `NEXT_PUBLIC_KAKAO_MAP_APP_KEY`를 카카오 JavaScript 키로 설정한다. 지도 키가 없어도 상세 화면에는 주소와 카카오맵 검색 링크가 표시된다.

## 첫 배포

1. Neon 프로젝트를 만들고 pooled 연결 문자열을 `DATABASE_URL`로 준비한다.
2. 배포 전에 Neon DB에 `pnpm db:migrate`를 실행한다. 합성 `db:seed`는 프리뷰에만 사용하고 실제 서비스 DB에는 넣지 않는다.
3. Google OAuth 웹 클라이언트에 `https://배포도메인/api/auth/callback/google`을 승인된 리디렉션 URI로 등록한다.
4. Vercel 프로젝트의 Root Directory를 `apps/web`으로 지정하고 `.env.example`의 서버 환경 변수를 등록한다.
5. `BETTER_AUTH_URL`은 실제 `https://` 배포 주소로, `DORAK_CONTACT_EMAIL`은 실제 응답 가능한 주소로 설정한다.
6. 실데이터를 검수해 넣기 전에는 `DORAK_ALLOW_INDEXING=false`를 유지한다.

Neon Free처럼 저장 공간이 제한된 배포에서는 원본 CSV를 별도로 보관하고, 원격 DB에는 검색에 필요한 정규화 결과만 배치 적재한다.

```bash
DATABASE_URL=postgresql://... pnpm data:import:seoul \
  /absolute/path/seoul-general-restaurants.csv \
  --batch-size=1000 --skip-raw
```

상세 절차와 production gate는 [DEPLOYMENT_ENVIRONMENTS.md](./docs/operations/DEPLOYMENT_ENVIRONMENTS.md)에 있다. CI는 임시 PostgreSQL에서 마이그레이션·시드·테스트·빌드·HTTP smoke를 매번 새로 실행한다.

## 제품 비전

도락이 사용자에게 제공해야 하는 가장 중요한 약속은 다음과 같다.

> 돈을 낸 식당이 아니라, 신뢰할 만한 리뷰어들에게 꾸준히 좋은 평가를 받은 식당이 위에 나온다.

이를 위해 다음 원칙을 지킨다.

- 광고 구매 여부를 평점에 반영하지 않는다.
- 광고, 추천, 평점순을 화면에서 명확히 구분한다.
- 대표 랭킹 단계에서는 단순 별점 평균만으로 순위를 만들지 않는다.
- 실제 방문이 확인된 리뷰에 높은 신뢰도를 부여한다.
- 리뷰어의 전문성을 음식 장르별로 계산한다.
- 폐업, 이전, 업종 변경 데이터를 지속해서 정리한다.
- 점수 계산 원칙과 업데이트 날짜를 공개한다.

## 플랫폼 구성

```text
소비자 앱
  검색 · 지도 · 리뷰 · 랭킹 · 저장 · 예약
             ↓
음식점 데이터/평점 플랫폼
  업소 DB · 중복 제거 · 점수 계산 · 부정 리뷰 탐지
             ↓
점주용 서비스
  매장 관리 · 리뷰 대응 · 광고 · 예약 · 고객관리
```

전국 확장이 가능한 데이터 모델은 유지하되, 실제 원장 적재와 사용자 콘텐츠는 선택한 1~2개 생활권과 우선 장르부터 단계적으로 넓힌다.

## 소비자 앱

- 현재 위치, 지역, 역, 동네 기반 검색
- 음식 장르, 가격, 영업시간, 주차, 혼밥, 단체석 등의 필터
- 지도와 목록 탐색
- 음식점 상세 페이지
- 메뉴, 가격, 영업시간, 사진
- 리뷰와 평점
- 리뷰어 프로필과 팔로우
- 가고 싶은 곳, 다녀온 곳, 개인 리스트
- 지역별·장르별 랭킹
- 예약과 웨이팅
- 한국어, 영어, 일본어, 중국어 지원
- 연간 어워드와 장르별 100대 식당

## 점주용 서비스

- 사업자 인증 및 매장 소유권 등록
- 메뉴, 가격, 사진, 영업시간 수정
- 임시 휴무와 재료 소진 공지
- 리뷰 답변과 이의 제기
- 방문, 검색, 저장, 예약 통계
- 유료 노출 상품
- 예약 슬롯, 테이블, 노쇼 관리
- 여러 지점의 통합 관리
- 외국어 메뉴 자동 번역

유료 상품은 평점에 영향을 주지 않아야 하며, 광고 노출은 일반 검색 결과와 명확히 구분한다.

## 운영자 시스템

- 신규, 폐업, 이전 음식점 검수
- 중복 음식점 병합
- 리뷰 신고 및 블라인드 처리
- 점주 이의 제기와 소명 기록
- 리뷰 조작 계정 조사
- 점수 재계산 및 버전 관리
- 사진과 메뉴의 저작권 신고 처리
- 모든 관리 작업의 감사 로그

도락의 운영 품질은 앱 기능만큼 중요하다. 음식점 데이터 정제와 리뷰 분쟁 처리를 처음부터 제품의 핵심 기능으로 취급한다.

## 전국 음식점 데이터

네이버, 카카오, 구글 등의 음식점 정보를 무단으로 수집해 자체 데이터베이스로 사용하지 않는다. 지도 사업자는 지도 표현과 검색 보조 수단으로 사용하고, 도락이 소유하고 관리하는 음식점 원장을 별도로 구축한다.

기본 데이터는 식품안전나라의 음식점 인허가, 변경, 폐업 데이터로 구성할 수 있다. 공공데이터로 음식점의 기본 뼈대를 만든 뒤 메뉴, 가격, 영업시간, 사진, 편의시설은 점주와 사용자 제보를 통해 자체 데이터로 축적한다.

### 핵심 데이터 모델

- `restaurant`: 도락 내부의 음식점 식별자
- `business_license`: 인허가 번호와 영업 상태
- `branch`: 실제 영업 지점
- `location`: 주소, 좌표, 행정구역
- `category`: 대분류 및 세부 음식 장르
- `menu`: 메뉴, 가격, 판매 상태
- `business_hours`: 요일별 영업시간과 브레이크타임
- `external_reference`: 공공데이터 및 지도 사업자의 외부 식별자
- `change_history`: 이전, 폐업, 상호 변경 기록

공공데이터의 변경분을 정기적으로 동기화하고 상호명, 주소, 전화번호, 인허가 번호를 바탕으로 중복 음식점을 탐지한다. 음식점의 이전과 지점 분리, 재개업은 단순 문자열 비교가 아닌 운영자 검수 흐름을 포함해야 한다.

## 평점 시스템

평점 시스템은 도락의 가장 중요한 지식재산이다. 점수 계산과 부정행위 탐지를 일반 애플리케이션 기능과 분리해 설계한다.

```text
공개 점수 =
리뷰어별 평가 기준 보정
× 장르 전문성
× 방문 인증 신뢰도
× 리뷰 품질
× 최신성
× 표본 수 보정
- 조작 위험도
```

### 기본 원칙

- 평소 높은 점수를 주는 사용자와 낮은 점수를 주는 사용자의 평가 기준을 정규화한다.
- 리뷰어의 전문성을 한식, 라멘, 커피 등 장르별로 분리한다.
- 리뷰가 적은 음식점의 점수가 지나치게 높아지지 않도록 베이지안 보정을 사용한다.
- 오래된 리뷰의 영향력을 점진적으로 낮춘다.
- 점주, 직원, 협찬 관계자의 평가는 공개할 수 있지만 평점 계산에서는 제외하거나 영향력을 제한한다.
- 동일 기기, 반복 사진, 비정상 방문 패턴, 계정 군집 등을 이용해 조작 위험도를 계산한다.
- 점수와 함께 리뷰 수, 방문 인증 비율, 최근 업데이트일을 표시한다.

알고리즘의 원칙은 공개하되, 조작에 활용될 수 있는 정확한 가중치와 탐지 규칙은 공개하지 않는다. 모든 점수 계산에는 알고리즘 버전을 기록하고 과거 점수를 재현할 수 있어야 한다.

## 방문 인증

방문 인증 리뷰와 일반 리뷰를 모두 허용하되 점수에 미치는 영향력을 다르게 설정한다.

- 도락을 통한 예약 완료
- 영수증 OCR 및 사업자번호 확인
- 결제 내역 연동
- 매장 QR 인증
- GPS 체크인과 시간 조건
- 촬영 사진의 메타데이터 확인
- 점주 확인

GPS는 방문 인증을 위한 보조 수단으로만 사용한다. 원본 위치 이력은 최소한으로 수집하고, 수집 목적이 끝나면 보관 정책에 따라 파기한다.

## 기술 구조

초기 배포는 사용자 화면, 운영 화면, API를 하나의 Next.js 애플리케이션으로 합친다. PostgreSQL 하나로 원장·검색·소량 배치를 처리하고 측정된 한계가 생길 때만 서비스를 추가한다.

- 사용자 웹·운영 화면·API: Next.js App Router
- 주 데이터베이스: Neon PostgreSQL + PostGIS
- 텍스트 검색: PostgreSQL FTS + `pg_trgm`
- 사진 및 파일: 실제 사진 기능부터 Cloudflare R2
- 저빈도 배치: GitHub Actions + PostgreSQL job
- 배포: Vercel Hobby
- 모바일 앱: 웹 핵심 흐름 검증 후 Expo + React Native
- 현재 제외: OpenSearch, Redis, ECS, RDS, 상시 워커

## 개발 단계

전체 제품을 설계하되 무료 인프라 안에서 데이터와 콘텐츠의 품질을 확보할 수 있도록 순차적으로 공개한다.

### 1단계: 데이터 기반

- 선택한 1~2개 생활권의 음식점 원장
- 검색, 지도, 음식점 상세 페이지
- 점주 인증
- 관리자용 데이터 정제 시스템

### 2단계: 리뷰 플랫폼

- 리뷰, 사진, 저장, 팔로우
- 방문 인증
- 리뷰어 신뢰도
- 평점 엔진
- 지역별·장르별 랭킹

### 3단계: 콘텐츠와 네트워크

- 전문 리뷰어 프로그램
- 에디터 추천
- 장르별 100대 식당
- 다국어 서비스
- 개인화 추천

### 4단계: 점주 사업

- 유료 매장 페이지
- 검색 광고
- 매장 분석 도구
- 리뷰 및 메뉴 관리

### 5단계: 거래 플랫폼

- 예약과 웨이팅
- 예약금과 노쇼 처리
- 테이블 관리
- 고객관계관리와 모바일 주문

## 필요한 조직

- 제품 책임자
- 모바일 앱 개발자
- 웹 개발자
- 백엔드 개발자
- 데이터 및 검색 엔지니어
- 제품 디자이너
- 음식점 데이터 운영자
- 리뷰 모더레이터
- 점주 영업 및 지원 담당자
- 법률 및 개인정보 자문

예약과 점주 운영 도구까지 직접 제공하는 단계에서는 기술 조직 외에도 음식점 영업, 고객 지원, 데이터 운영, 리뷰 분쟁 처리 조직이 필요하다.

## 법률 및 정책 검토

- 도락의 독립적인 상표와 디자인을 사용하고 타베로그의 명칭, UI, 문구, 알고리즘을 복제하지 않는다.
- 리뷰 이용약관, 콘텐츠 라이선스, 신고 및 이의 제기 절차를 마련한다.
- 개인정보는 서비스 제공에 필요한 최소 범위로 수집한다.
- 위치정보 수집 및 위치기반서비스 신고 대상 여부를 출시 전에 검토한다.
- 영수증과 위치 인증 원본의 보관 기간을 최소화한다.
- 광고성 리뷰와 협찬 관계의 표시 기준을 정한다.
- 점주의 반론권과 사용자의 표현권을 함께 고려한 리뷰 운영 정책을 수립한다.

## 초기 성공 지표

- 검색 가능한 음식점의 데이터 정확도
- 지역 및 장르별로 리뷰 5개 이상을 보유한 음식점 비율
- 방문 인증 리뷰 비율
- 리뷰 신고 중 실제 위반으로 판정된 비율
- 검색에서 상세 보기, 저장, 길 찾기, 예약으로 이어지는 전환율
- 핵심 리뷰어의 월간 재방문율
- 점주 인증 완료 매장 수
- 중복 및 폐업 데이터의 처리 시간
