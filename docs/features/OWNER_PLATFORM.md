# 도락 점주 플랫폼 설계

> 상태: 초안 v0.1  
> 대상: 독립 점주, 매장 관리자, 다점포 운영자, 프랜차이즈 본사, 대행사  
> 원칙: 점주에게 공식 정보와 운영 권한을 주되 리뷰·평점·자연 검색의 독립성은 판매하지 않는다.  
> 연관 문서: [PRODUCT.md](../product/PRODUCT.md), [DATA_MODEL.md](../architecture/DATA_MODEL.md), [OPERATIONS.md](../operations/OPERATIONS.md), [RESERVATION_SYSTEM.md](./RESERVATION_SYSTEM.md)

---

## 1. 목적

점주 플랫폼은 광고 콘솔이 아니라 도락 음식점 원장을 최신 상태로 유지하고, 사용자와 공식적으로 소통하며, 예약 운영을 관리하는 업무 제품이다.

다음 목표를 갖는다.

- 실제 권한이 있는 사람이 지점을 안전하게 claim한다.
- 개인 계정 공유 없이 직원과 대행사의 역할을 관리한다.
- 점주 제출 정보가 출처와 검증 이력을 가진 공식 assertion이 된다.
- 리뷰에 답하고 정책 위반을 신고할 수 있지만 점수나 자연 노출을 구매할 수 없다.
- 예약 연락처와 분석 데이터는 업무상 필요한 범위에서만 보인다.
- 독립점부터 다점포·프랜차이즈까지 같은 권한 모델로 확장한다.
- 유료 상품 해지와 광고 집행이 기본 정보·리뷰 권리에 영향을 주지 않는다.

## 2. 제품 원칙

### 2.1 지점 페이지는 점주의 소유물이 아니다

지점 페이지는 도락의 공공적 음식점 원장과 사용자 콘텐츠를 결합한 서비스 리소스다. 점주는 공식 정보의 강한 출처이지만 사용자 리뷰를 임의 편집·삭제하거나 과거 사실을 지울 수 없다.

### 2.2 claim은 계정 소유권이 아니라 권한 관계다

점주 계정을 음식점 행에 직접 꽂지 않는다. 사용자 계정이 조직의 구성원이 되고, 조직이 검증된 지점 범위 권한을 갖는다.

### 2.3 점주 정보도 검증과 이력을 거친다

점주가 입력했다고 모든 필드가 즉시 공개되지는 않는다. 영업시간이나 메뉴는 빠르게 반영할 수 있지만 법적 상호, 폐업 취소, 위치 이전처럼 정체성에 영향을 주는 변경은 검토한다.

### 2.4 직원 계정 공유를 유도하지 않는다

하나의 아이디를 돌려 쓰면 퇴사자 접근 차단, 변경 책임, 추가 인증이 불가능하다. 개인별 계정과 조직 역할을 사용한다.

### 2.5 유료와 신뢰 기능을 분리한다

광고, 고급 분석, 예약 부가 기능은 판매할 수 있다. 다음은 구매 여부와 무관해야 한다.

- 기본 claim과 핵심 정보 정정
- 리뷰 공식 답글과 정책 신고
- 계정 보안과 권한 관리
- 예약 거래에 필요한 기본 운영·분쟁 처리
- 평점 계산과 자연 검색 관련도

## 3. 사용자 유형

### 3.1 독립 점주

한두 개 매장을 직접 운영한다. 모바일에서도 영업시간, 휴무, 예약을 빠르게 바꿀 수 있어야 하며 복잡한 조직 설정을 강요하지 않는다.

### 3.2 매장 관리자

특정 지점의 정보·예약을 관리한다. 조직 결제, 전체 지점, 소유권 이전 권한은 없다.

### 3.3 다점포 운영자

여러 지점의 메뉴·영업시간·성과를 비교한다. 공통 템플릿과 지점별 예외, 대량 변경, 승인 흐름이 필요하다.

### 3.4 프랜차이즈 본사

브랜드 표준 정보와 일부 지점 권한을 갖지만 가맹점의 실제 영업·예약 권한과 충돌할 수 있다. 브랜드 권한과 지점 운영 권한을 분리한다.

### 3.5 대행사

한 명이 여러 고객 조직에 제한된 기간 접근한다. 조직 간 데이터가 섞이지 않도록 명시적 전환과 재인증을 요구한다.

### 3.6 점주 고객지원·운영자

점주를 대신해 로그인하지 않는다. 사건 기반 제한 뷰와 감사되는 명령으로 지원한다.

## 5. 조직 모델

### 5.1 `owner_organization`

```text
id
organization_type
display_name
legal_entity_ref
verification_status
security_policy
billing_profile_ref
status
created_at
```

조직 유형:

```text
independent_owner
restaurant_group
franchise_headquarters
franchisee
agency
management_company
```

### 5.2 조직 관계

프랜차이즈 본사와 가맹점 조직을 하나로 합치지 않는다.

```text
parent_organization_id
child_organization_id
relationship_type
scope
effective period
verification status
```

관계 예:

- 본사→가맹점: 브랜드 자료 배포
- 운영회사→지점 법인: 예약 관리
- 대행사→고객 조직: 콘텐츠 편집

관계가 있다고 자동으로 모든 데이터에 접근하지 않는다.

### 5.3 구성원

```text
organization_member
  user_account_id
  organization_id
  role assignments
  branch scopes
  status
  invited_by
  joined_at
  last_access_at
```

상태:

```text
invited -> active -> suspended -> active
invited -> expired
active -> removed
```

### 5.4 조직 전환

여러 조직 구성원은 현재 조직과 지점 문맥을 화면 상단에서 명확히 본다. 쓰기 요청에는 서버가 검증한 organization context를 포함하고, URL의 조직 ID만 바꿔 다른 조직에 접근할 수 없게 한다.

## 6. 역할과 권한

### 6.1 기본 역할

| 역할 | 핵심 권한 |
|---|---|
| `owner` | 소유권, 구성원, 구독, 모든 허용 지점 |
| `admin` | 구성원·지점 운영, 소유권 이전 제외 |
| `editor` | 공식 정보, 메뉴, 사진 |
| `reservation_manager` | 예약·좌석·연락처 제한 접근 |
| `analyst` | 집계 분석 읽기 |
| `billing` | 청구·구독·광고 결제 |
| `review_manager` | 공식 답글·신고 |

역할은 권한 묶음이며 API에서는 세부 권한을 검사한다.

### 6.2 권한 예

```text
branch.profile.read
branch.profile.propose
branch.hours.write
branch.menu.write
branch.media.write
review.read
review.respond
review.report
reservation.read
reservation.contact.reveal
reservation.confirm
reservation.cancel
reservation.policy.write
analytics.read
member.invite
member.manage
billing.manage
owner.transfer
audit.read
```

### 6.3 지점 범위

권한 부여는 다음 교집합이다.

```text
organization relationship
AND role permissions
AND branch scope
AND membership status
AND resource state
AND step-up authentication if required
```

### 6.4 사용자 지정 역할

엔터프라이즈 단계 전에는 임의 권한 조합을 제한한다. 과도한 유연성은 권한 검토와 지원을 어렵게 한다. 필요하면 기본 역할 복제 + 허용된 소수 권한 조정으로 제공한다.

### 6.5 권한 검토

- 조직 owner는 분기별 구성원 검토 알림을 받는다.
- 90일 이상 미사용 고위험 권한을 표시한다.
- 퇴사·계약 종료 시 즉시 해제한다.
- 대행사 접근에는 만료일을 필수로 한다.
- owner가 한 명뿐이면 제거 전 후속 owner를 요구한다.

## 7. 지점 claim

### 7.1 상태 머신

```text
draft
 -> submitted
 -> verifying_identity
 -> verifying_authority
 -> conflict_review
 -> approved
 -> rejected
 -> withdrawn

approved -> suspended
approved -> revoked
approved -> transfer_pending -> transferred
any active -> disputed
```

### 7.2 신청 입력

- 도락 지점 선택 또는 신규 지점 후보
- 신청 조직
- 신청자의 역할
- 사업자·영업 관련 증빙
- 대표자 또는 위임 증빙
- 공식 연락 수단
- 요청하는 지점 범위와 기능

필요 이상의 주민등록번호나 서류 전체를 기본 수집하지 않는다.

### 7.3 자동 확인

- 사업자 정보의 형식과 유효 상태
- 지점 상호·주소 매칭
- 공식 연락 수단 확인
- 동일 사업자·전화·도메인의 기존 조직
- 기존 승인 claim 충돌
- 반복 신청·조작 위험

자동 확인은 승인 추천이지 최종 소유권 판정이 아닐 수 있다.

### 7.4 사람 검토

필요 조건:

- 기존 claim과 충돌
- 법적 상호와 공개 브랜드가 크게 다름
- 대행사·위임 관계
- 프랜차이즈 본사와 가맹점 권한 충돌
- 신규 지점 생성 동반
- 서류 변조 또는 계정 위험 신호

### 7.5 승인 결과

승인 시 생성:

```text
organization-branch authority relation
initial role and branch scope
claim decision record
policy acknowledgement
security onboarding task
official profile completion task
```

### 7.6 거절과 재신청

내부 탐지 규칙을 누설하지 않는 범위에서 이유 범주와 보완 경로를 제공한다. 다른 증거가 준비되면 새 신청 또는 이의 제기가 가능하다.

### 7.7 소유권 분쟁

- 기존 owner를 자동 해제하지 않는다.
- 양측이 상대 증빙 원본을 볼 수 없다.
- 예약 운영 연속성을 위해 기능별 임시 권한을 정할 수 있다.
- 고위험 정보 수정과 구성원 초대를 일시 잠글 수 있다.
- 결정자와 실행자를 분리한다.
- 결과와 이의 경로를 양측에 통지한다.

## 8. 소유권 이전

### 8.1 이전이 필요한 경우

- 매매·양도
- 법인 변경
- 프랜차이즈 가맹주 변경
- 운영회사 변경
- 잘못 승인된 claim 정정

### 8.2 음식점 정체성과 구분

소유자가 바뀌어도 음식점 정체성이 유지될 수 있고, 같은 장소에 완전히 새 음식점이 생길 수 있다. claim 이전과 branch 승계를 별도로 판단한다.

### 8.3 이전 절차

1. 새 조직과 권한을 검증한다.
2. 기존 조직에 통지한다.
3. 지점 정체성 유지 여부를 Data Ops가 검토한다.
4. 활성 예약, 구독, 광고, 정산 영향을 계산한다.
5. 효력 시각을 정한다.
6. 새 owner 권한을 활성화하고 이전 권한을 종료한다.
7. 예약 연락처와 과거 분석 접근 범위를 정책대로 분리한다.
8. 감사 기록과 양측 결과를 남긴다.

과거 예약자 연락처와 직원 메모를 새 소유자에게 자동 승계하지 않는다.

## 9. 공식 정보 관리

### 9.1 정보 분류

| 분류 | 예 | 공개 방식 |
|---|---|---|
| Identity | 상호, 지점명, 주소, 사업 상태 | 검토 가능 |
| Operations | 영업시간, 휴무, 전화 | 빠른 반영 + 출처 |
| Offering | 메뉴, 가격, 코스 | 빠른 반영 + 스냅샷 |
| Amenities | 주차, 접근성, 유아, 좌석 | 구조화 + 검증 신호 |
| Editorial | 소개, 공지 | 공식 표시, 검색 영향 제한 |
| Transaction | 예약 정책, 취소, 예약금 | 버전·동의·감사 필수 |

### 9.2 변경 상태

```text
draft -> submitted -> published
                   -> pending_review -> published
                                     -> rejected
published -> superseded
```

### 9.3 자동 반영 후보

- 정상 범위의 영업시간
- 특정 날짜 임시 휴무
- 메뉴 가격·판매 상태
- 공식 소개
- 공식 사진 순서

자동 반영도 출처와 작성자를 기록하며 이상 변경은 사후 검토할 수 있다.

### 9.4 검토 필수 후보

- 주소·좌표 대폭 변경
- 폐업 상태 해제
- 상호·브랜드 정체성 변경
- 다른 지점과 병합 요청
- 주류·연령·안전 관련 분류
- 사용자 리뷰를 무효화할 수 있는 재개업 주장

### 9.5 충돌 해결

공공 데이터, 점주, 사용자 제보가 충돌하면 필드별 assertion을 비교한다. 점주가 현재 임시 휴무의 가장 강한 출처일 수 있지만 법적 영업 상태의 유일한 출처는 아니다.

### 9.6 예약에 미치는 변경

영업시간·휴무·코스·정책 변경 전 활성 예약 영향을 보여 준다. 기존 예약을 자동으로 새 정책에 옮기지 않는다.

## 10. 영업시간과 휴무

### 10.1 편집 모델

- 요일별 복수 영업 구간
- 브레이크 타임
- 라스트 오더
- 자정 이후 영업
- 정기 휴무
- 공휴일 예외
- 특정일 휴무·특별 영업
- 임시 휴업 기간

### 10.2 검증

- 구간 겹침
- 종료가 시작보다 빠른 자정 처리
- 브레이크가 영업 구간 밖인지
- 예약 서비스 구간과의 충돌
- 휴무일의 활성 예약
- 지나치게 장기인 임시 상태

### 10.3 만료 알림

임시 영업시간, 휴무, 공지는 만료일을 가져야 한다. 만료 시 이전 정기 규칙으로 복귀하되 공개 결과를 미리 보여 준다.

## 11. 메뉴와 코스

### 11.1 메뉴 구조

```text
menu
 ├─ section
 │   └─ item
 │       ├─ option group
 │       ├─ price variant
 │       ├─ allergen/dietary declaration
 │       └─ media
 └─ publication schedule
```

### 11.2 가격

- 통화 최소 단위 정수
- 세금 포함·별도
- 1인/테이블/변동 가격
- 시간대·요일 가격
- `market_price` 같은 비고정 가격
- 과거 예약 코스 스냅샷

### 11.3 알레르기와 식이 정보

점주 입력을 의료적 보증처럼 표현하지 않는다. 입력 시 확인 일자와 교차오염 고지를 제공한다. 사용자 자유 태그가 공식 점주 선언으로 바뀌지 않게 한다.

### 11.4 대량 편집

- CSV 가져오기 전 dry-run
- 행별 오류
- 변경 요약
- 영향 개수 임계치
- 예약 코스 참조 확인
- 부분 성공 결과
- 이전 버전 복구

### 11.5 메뉴 검색 영향

점주가 키워드 목록을 채워 검색을 조작할 수 없게 실제 공개 메뉴명·설명과 구조화 카테고리를 색인한다. 반복 키워드와 관련 없는 지역·장르 텍스트는 관련도 이득을 제한한다.

## 12. 공식 사진과 소개

### 12.1 사진 유형

```text
logo
exterior
interior
menu
dish
seat/room
accessibility
official_event
```

### 12.2 권리 확인

업로더는 사용할 권리가 있음을 확인한다. 인물, 전화번호, 차량번호, 영수증 등 불필요한 개인정보를 검사한다.

### 12.3 표시

점주 사진은 `공식` 출처로 표시하고 사용자 사진과 섞이더라도 필터 가능하게 한다. 유료 여부로 사용자 사진을 숨기거나 공식 사진만 강제하지 않는다.

### 12.4 생성·과도 보정 이미지

실제 메뉴·공간을 오해하게 하는 합성 이미지는 공식 사실 사진으로 사용하지 못하게 할 수 있다. AI 생성 또는 연출 이미지의 허용 범위와 표시를 정책화한다.

## 13. 리뷰 관리

### 13.1 점주가 할 수 있는 일

- 자기 지점의 공개 리뷰 읽기
- 공식 답글 작성·수정·삭제
- 정책 위반 신고
- 방문 여부 검토 요청
- 운영 사건 상태 확인
- 충분한 표본에서 주제 집계 확인

### 13.2 할 수 없는 일

- 리뷰 원문 편집
- 별점 변경
- 답글 구매로 노출 상승
- 신고만으로 즉시 삭제
- 작성자의 비공개 연락처·방문 이력 확인
- 부정적 리뷰어를 예약에서 자동 차별
- 리뷰 삭제 대가 제공

### 13.3 공식 답글

답글은 조직명으로 공개하고 실제 작성 구성원은 감사에 남긴다.

상태:

```text
draft -> published -> edited -> deleted
                   -> limited/removed by moderation
```

금지 예:

- 작성자 개인정보 공개
- 위협·보복
- 할인 제공 조건으로 리뷰 수정 요청
- 방문 증빙 원본 요구
- 근거 없는 범죄·질병 주장

### 13.4 신고 남용

점주별 신고량과 인용률을 분석한다. 반복적으로 의견 차이를 정책 위반으로 신고하는 조직에는 교육, 신고 제한, 심각한 경우 권한 제재를 적용할 수 있다.

### 13.5 주제 분석

충분한 공개 리뷰에서 다음을 집계할 수 있다.

- 음식 맛·온도·양
- 서비스·친절·응답
- 대기·예약
- 분위기·소음
- 가격 가치
- 접근성·편의시설

개별 리뷰어를 추론할 수 있는 작은 집단은 숨긴다. 생성 요약에는 오류 신고와 근거 기간을 표시한다.

리뷰 방문 인증을 막기 위해 실제 방문을 노쇼로 표시하거나, 평점을 높이기 위해 허위 완료 처리하는 패턴을 모니터링한다. 정정 이력은 삭제하지 않는다.

## 16. 알림

### 16.1 유형

| 유형 | 예 |
|---|---|
| Security | 로그인, 권한, 구성원 변경 |
| Operational | claim, 정보 검수, 예약, 환불 |
| Review | 새 리뷰, 답글 상태, 신고 결과 |
| Data quality | 영업시간 만료, 충돌, 수정 요청 |
| Product | 기능 안내, 교육 |
| Marketing | 광고·유료 상품 프로모션 |

보안·거래 알림은 마케팅 동의와 분리한다.

### 16.2 역할 기반 라우팅

예약 알림을 조직 owner 모두에게 보내지 않는다. 지점과 역할별 수신자를 정하며 최소 한 명의 fallback을 요구한다.

### 16.3 에스컬레이션

승인형 예약 응답이 임박하면:

```text
primary push/web
 -> fallback SMS if configured
 -> backup reservation manager
 -> auto-expiry and user notification
```

## 17. 구독과 유료 상품

### 17.1 상품 경계

후보:

- 예약대장 고급 기능
- 고급 분석과 내보내기
- 다점포 관리
- 추가 구성원·승인 흐름
- POS·외부 채널 연결
- 명확히 표시된 광고 캠페인

### 17.2 기본 무료 권리

유료 해지 후에도 다음은 유지한다.

- claim된 지점의 핵심 정보 수정
- 구성원 보안 관리에 필요한 최소 기능
- 리뷰 답글·신고
- 법적·개인정보 요청
- 과거 예약 거래와 환불 처리에 필요한 접근

### 17.3 구독 상태

```text
trialing -> active -> past_due -> grace_period -> suspended -> cancelled
active -> cancellation_scheduled -> cancelled
```

구독 상태가 자연 검색 점수나 공개 평점을 바꾸지 않는다.

### 17.4 해지

- 효력 시각과 남은 기능을 사전 표시한다.
- 데이터 내보내기 기회를 제공한다.
- 공개 음식점 정보는 삭제하지 않는다.
- 고급 집계 접근만 종료한다.
- 예약 거래가 있으면 필요한 운영 기능을 유지한다.

### 17.5 광고

- 자연 검색과 별도 placement
- 광고 표시 문구
- campaign·creative 검수
- 자연 결과와 동일 지점 중복 규칙
- 민감 타기팅 제한
- 광고 성과와 자연 성과 분리
- 광고 구매가 리뷰 운영 결정에 영향 없음

## 22. 상태와 기능 저하

### 22.1 원장 검수 지연

점주 제출을 `검토 중`으로 표시하고 현재 공개 값과 제안 값을 함께 보여 준다. 같은 변경을 반복 제출하게 하지 않는다.

### 22.2 분석 지연

마지막 갱신 시각과 잠정 상태를 표시한다. 잘못된 0을 보여 주지 않는다.

### 22.3 예약 장애

- 예약대장 마지막 읽기 스냅샷
- 신규 즉시 확정 차단
- 전화·지원 대안
- 수동 변경의 충돌 위험 고지
- 복구 후 재조정

### 22.4 알림 장애

웹 콘솔의 오늘 할 일을 최종 진실로 유지한다. 문자·푸시 성공을 예약 처리의 필수 커밋 조건으로 삼지 않는다.

## 26. 출시 전 체크리스트

- [ ] 기존 claim 충돌이 자동 권한 탈취로 이어지지 않는다.
- [ ] 조직·역할·지점 범위의 객체 권한 테스트가 통과한다.
- [ ] 메뉴 편집자는 예약 연락처를 볼 수 없다.
- [ ] owner가 한 명뿐일 때 안전한 이전·복구가 가능하다.
- [ ] 핵심 정보 변경에 출처·작성자·버전이 남는다.
- [ ] 휴무 변경이 활성 예약에 미치는 영향을 보여 준다.
- [ ] 점주 신고가 리뷰 즉시 삭제로 이어지지 않는다.
- [ ] 광고·구독이 자연 검색·평점과 분리된다.
- [ ] 점주 분석에서 작은 수와 사용자 식별이 보호된다.
- [ ] 예약 연락처 보기·복사가 감사된다.
- [ ] 구독 해지 후 기본 권리와 거래 지원이 유지된다.
- [ ] 모바일과 접근성 경로에서 임박 예약을 처리할 수 있다.
- [ ] 점주 계정 탈취 runbook이 있다.

- 공식 정보 자동 반영 필드와 위험 임계치

- 점주 분석 작은 수 임계치
- 무료 예약대장과 유료 기능 경계
- 구독 요금 단위: 조직, 지점, 예약량, 기능
- 광고 상품 형식과 슬롯 수
