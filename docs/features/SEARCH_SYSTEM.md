# 도락 검색 및 지도 탐색 설계

> 실행 우선순위 안내: 검색의 제품 원칙과 평가 방식은 유지하되 현재 구현 엔진은 PostgreSQL FTS + `pg_trgm` + PostGIS다. 아래 OpenSearch 전용 mapping·indexer·장애 항목은 [비용 우선 운영안](../architecture/COST_FIRST_ARCHITECTURE.md)의 도입 문턱을 넘긴 뒤 사용하는 확장 참고안이다.

## 1. 목적

이 문서는 도락의 통합 검색, 자동완성, 한글 분석, 지도 영역 탐색, 필터, 검색 랭킹, 광고 분리, 색인 동기화, 품질 평가를 정의한다.

도락 검색은 단순히 음식점 이름이 포함된 문서를 찾는 기능이 아니다. 사용자가 다음과 같은 다양한 의도를 표현할 수 있어야 한다.

- `정식당`처럼 정확한 상호 찾기
- `성수 라멘`처럼 지역과 장르 조합
- `강남역 2만원대 조용한 일식`처럼 조건 조합
- `지금 영업 중인 혼밥 가능한 곳`처럼 상황 탐색
- `망원동 딤섬`처럼 결과가 적을 때 인접 개념 탐색
- 지도를 움직이며 해당 화면 안의 음식점 찾기
- 과거 상호, 오탈자, 초성, 영문명으로 찾기

## 2. 검색 원칙

### SS-P01. 자연 검색과 광고를 분리한다

광고 구매 여부는 자연 검색 점수, 평점순, 공식 랭킹에 영향을 주지 않는다. 광고는 별도 후보·경매·정책을 거쳐 명시된 슬롯에 제공한다.

### SS-P02. 품질과 관련성을 구분한다

사용자가 정확한 상호를 검색하면 평점이 낮아도 해당 음식점이 먼저 나와야 한다. 탐색형 검색에서는 관련성 안에서 공개 점수와 데이터 신뢰도를 활용한다.

### SS-P03. 인기만으로 결과를 지배하지 않는다

조회·저장·예약 같은 인기도는 제한된 보조 신호다. 대형 프랜차이즈와 유명 지역이 항상 상단을 차지하지 않도록 포화와 다양화 규칙을 적용한다.

### SS-P04. 폐업과 불확실성을 숨기지 않는다

폐업 지점은 일반 탐색에서 제외하지만 정확한 상호 검색이나 과거 링크에서는 상태와 이전 관계를 보여준다.

### SS-P05. 사용자 위치는 선택 사항이다

위치 권한 없이도 지역명, 지도 이동, 저장 지역으로 전체 검색 기능을 이용할 수 있어야 한다.

### SS-P06. 검색 엔진은 원장이 아니다

OpenSearch 장애 또는 색인 오류가 음식점 원장과 리뷰를 변경하지 않는다. 모든 검색 문서는 PostgreSQL에서 재생성 가능해야 한다.

### SS-P07. 설명 가능한 정렬을 제공한다

관련도순, 도락 점수순, 거리순, 리뷰 많은 순, 신규순 등 사용자가 선택한 정렬의 의미를 유지한다. 관련도순에 광고나 숨은 계약 신호를 섞지 않는다.

## 3. 검색 대상

### 3.1 검색 엔터티

- 음식점 지점
- 메뉴 및 대표 음식
- 지역과 역·상권
- 음식 장르와 이용 목적
- 리뷰어
- 공개 리스트
- 에디터 콘텐츠
- 어워드와 랭킹 페이지

### 3.2 결과 그룹

통합 검색은 결과 유형을 섞되 의도에 따라 그룹을 제공한다.

```text
바로가기
  지역 · 장르 · 역

음식점
  지점 단위 결과

메뉴
  해당 메뉴를 제공하는 음식점

리뷰어·리스트
  사람과 큐레이션
```

음식점 검색 화면에서는 음식점 결과를 기본으로 하고 다른 엔터티는 제안 영역에 둔다.

## 4. 사용자 검색 의도

### 4.1 Exact Place

특정 상호 또는 지점을 찾는다.

예시:

- `정식당`
- `오레노라멘 본점`
- `런던베이글 안국`

우선 신호:

- 정규화 상호 정확 일치
- 지점명 정확 일치
- 과거 상호 및 별칭
- 지역과 지점명의 일치

### 4.2 Category in Area

특정 지역의 음식 장르를 찾는다.

예시:

- `성수 파스타`
- `부산 돼지국밥`
- `을지로 노포`

우선 신호:

- 지역 엔터티 인식
- 대표·보조 카테고리
- 지리 범위
- 품질과 거리의 균형

### 4.3 Dish Search

특정 메뉴를 찾는다.

예시:

- `마파두부`
- `시오라멘`
- `글루텐프리 디저트`

메뉴 원장, 사용자 리뷰의 주문 메뉴, 점주 공식 메뉴를 구분하고 공식·최신 메뉴에 높은 신뢰도를 부여한다.

### 4.4 Attribute Search

이용 조건을 찾는다.

예시:

- `혼밥`
- `주차 가능한 한식`
- `아기 의자 있는 식당`
- `조용한 데이트`

공식 구조화 정보, 반복 사용자 태그, 리뷰 텍스트를 출처별로 구분한다. 한 명의 리뷰 표현을 확정 시설 정보처럼 사용하지 않는다.

### 4.5 Availability Search

현재 또는 특정 시각에 이용 가능한 음식점을 찾는다.

예시:

- `지금 영업 중`
- `오늘 8시 4명 예약`
- `새벽 1시 식사`

영업시간과 예약 재고는 검색 문서의 캐시 시각을 표시하고 예약 확정 전에 원장에서 다시 확인한다.

### 4.6 Discovery

명확한 상호 없이 새로운 후보를 찾는다.

예시:

- `오늘 뭐 먹지`
- `근처 평점 높은 곳`
- `기념일 저녁`

전체 품질, 취향, 거리, 가격, 영업 여부, 다양성을 사용하되 개인화 결과와 전체 공개 점수를 구분한다.

## 5. 검색 요청 모델

개념 API:

```json
{
  "query": "성수 조용한 파스타",
  "entityTypes": ["branch"],
  "location": {
    "center": { "lat": 37.5445, "lon": 127.056 },
    "bounds": null,
    "regionCode": null
  },
  "filters": {
    "categoryIds": [],
    "priceBands": [],
    "openAt": null,
    "reservation": null,
    "features": []
  },
  "sort": "relevance",
  "page": {
    "cursor": null,
    "limit": 20
  },
  "locale": "ko-KR"
}
```

클라이언트가 검색 엔진 DSL을 직접 전송하지 않는다. API는 허용된 필터와 정렬만 내부 쿼리로 변환한다.

## 6. 쿼리 처리 파이프라인

```text
입력
  ↓
유니코드·공백·기호 정규화
  ↓
언어·초성·로마자 패턴 판별
  ↓
지역·장르·메뉴·상호 엔터티 인식
  ↓
명시 필터와 쿼리 조건 병합
  ↓
텍스트·지리 후보 생성
  ↓
자연 검색 점수 계산
  ↓
상태·정책 필터
  ↓
다양화와 중복 지점 처리
  ↓
별도 광고 슬롯 결합
  ↓
설명 가능한 응답
```

### 6.1 입력 제한

- 최대 쿼리 길이 제한
- 제어문자 제거
- 과도한 와일드카드 및 정규식 미지원
- 사용자 입력을 `query_string` DSL에 직접 삽입하지 않음
- 필터 배열과 지도 경계 크기 제한
- 자동완성은 더 짧은 타임아웃과 결과 수 제한

## 7. 한글과 다국어 분석

### 7.1 필드 다중화

상호명은 하나의 분석 필드만 사용하지 않는다.

```text
name.display          원문 표시
name.keyword          정확 일치용 정규화 keyword
name.ko               한국어 형태 분석
name.ngram            자동완성과 부분 일치
name.initials         한글 초성
name.romanized        공식·검증된 로마자 별칭
name.aliases          과거 상호와 일반 별칭
```

### 7.2 정규화

- Unicode 정규화
- 연속 공백 축소
- 영문 소문자화
- 전각·반각 통일
- 일반적인 지점 접미사 분리
- 특수문자 제거 버전과 원문 버전 병행
- `&`, `앤드`, `and` 등 제한된 동의어

상호의 법적·표시 이름 원문은 변경하지 않는다.

### 7.3 한국어 형태 분석

OpenSearch `analysis-nori` 플러그인을 기본 후보로 사용한다. 음식점명은 일반 문장과 다르므로 다음을 실제 검색 로그와 평가셋으로 검증한다.

- 복합명사 분해 방식
- 조사와 어미 처리
- 사용자 사전
- 외래어와 고유명사
- 띄어쓰기 없는 상호
- 한자와 한글 혼용

Nori 분석 결과만 사용하지 않고 정확 일치와 n-gram 필드를 함께 검색한다.

### 7.4 초성 검색

애플리케이션 색인 빌더에서 한글 음절의 초성을 파생한다.

예시:

- `오레노라멘` → `ㅇㄹㄴㄹㅁ`
- `런던베이글뮤지엄` → `ㄹㄷㅂㅇㄱㅁㅈㅇ`

초성 필드는 사용자의 입력이 초성 패턴일 때만 강하게 검색한다. 일반 텍스트 쿼리에 초성 일치를 섞어 노이즈를 만들지 않는다.

### 7.5 로마자와 외국어

- 점주 공식 영문명
- 서비스 검수 번역명
- 일반적으로 사용되는 표기
- 제한적인 자동 로마자 변환

자동 로마자 변환은 후보 검색에만 사용하고 공식 이름처럼 표시하지 않는다. 일본어·중국어 음식명은 원어와 한국어 별칭을 연결하되 의미가 다른 메뉴를 과도하게 합치지 않는다.

### 7.6 동의어

동의어 유형:

- 음식명: `돈카츠`, `돈가스`
- 장르: `중식`, `중국요리`
- 지역 별칭: `경리단`, `경리단길`
- 역·상권: `강남역`, `강남`
- 외래어 표기: `딤섬`, `딤쌈`

동의어는 방향성을 가질 수 있다. `강남`을 항상 `강남역`으로 확장하지 않는다.

동의어 변경은 버전, 근거, 영향 쿼리, 작성자, 승인자를 기록한다.

### 8.2 색인하지 않는 데이터

- 사용자 이메일과 전화번호
- 예약자 정보
- 정밀 사용자 위치
- 비공개 리뷰와 신고 증빙
- 리뷰어 내부 영향력
- 조작 위험 점수
- 광고 계약 및 매출
- 점주 사업자 서류

### 8.3 메뉴 데이터

대표 메뉴명과 활성 구조화 메뉴를 검색 문서에 포함한다. 전체 메뉴 설명과 옵션을 무제한 중첩하지 않는다. 긴 메뉴는 별도 메뉴 인덱스를 사용하거나 대표 토큰만 지점 문서에 포함한다.

## 9. 자연 검색 관련도

### 9.1 텍스트 관련도

필드 우선순위 예시:

1. 정규화 상호 정확 일치
2. 상호·지점명 phrase 일치
3. 공식 별칭 및 과거 상호 일치
4. 대표 메뉴 정확 일치
5. 대표·보조 장르 일치
6. 지역·역·상권 일치
7. 속성 및 리뷰 집계 태그 일치
8. 리뷰 본문 제한적 일치

리뷰 본문에서 한 번 언급됐다는 이유로 음식점의 공식 속성처럼 높은 점수를 주지 않는다.

### 9.2 개념 점수식

```text
relevance_score =
  text_relevance
  × exact_intent_boost
  × geographic_relevance
  × operational_factor
  × quality_factor
  × data_confidence_factor
  × bounded_popularity_factor
  × freshness_factor
```

각 곱셈 성분에는 하한과 상한을 둔다. 특정 신호 하나가 텍스트 불일치 결과를 상단으로 끌어올리지 못하게 한다.

### 9.3 품질 신호

공개 도락 점수를 사용할 수 있지만 다음 조건을 지킨다.

- 정확 상호 검색을 뒤집지 않는다.
- 점수 집계 중 음식점을 검색에서 제거하지 않는다.
- 불확실성이 큰 점수의 영향력을 제한한다.
- 광고·점주 계약 신호와 결합하지 않는다.

### 9.4 인기도

후보 신호:

- 고유 사용자 상세 조회
- 저장
- 길 찾기
- 예약 시도와 완료
- 최근 리뷰 활동

보정:

- 로그 포화
- 봇·내부 트래픽 제외
- 지역과 장르 기준선
- 이벤트성 급증 제한
- 장기 유명세보다 최근 유용성 반영

인기도는 음식점 품질 점수로 표시하지 않는다.

### 9.5 영업 상태

- 사용자가 `지금 영업 중`을 선택하면 확정 필터로 사용한다.
- 일반 관련도순에서는 영업 중을 가볍게 우대할 수 있지만 닫힌 정확 상호를 숨기지 않는다.
- 임시 휴무와 폐업을 구분한다.
- 영업시간 신뢰도가 낮으면 `영업 중`을 단정하지 않는다.

## 10. 정렬 모드

### 10.1 관련도순

쿼리 일치, 거리, 공개 품질, 상태, 제한된 인기도를 결합한다.

### 10.2 도락 점수순

- 공개 점수 자격이 있는 음식점만 점수로 정렬한다.
- 점수 미표시 음식점을 결과 끝에 별도 그룹으로 둘 수 있다.
- 같은 점수 구간에서는 불확실성, 관련도, 거리 순의 명시된 보조 기준을 사용한다.
- 공식 랭킹과 일반 점수순은 동일하지 않을 수 있음을 안내한다.

### 10.3 거리순

- 사용자 중심점 또는 지도 중심점을 요구한다.
- 정확 상호 검색과 충돌할 때는 정확 결과를 상단 바로가기로 제공할 수 있다.
- 좌표 신뢰도가 낮은 지점은 표시하되 거리 정밀성을 과장하지 않는다.

### 10.4 리뷰 많은 순

전체 리뷰 수보다 적격 리뷰 수를 기본으로 한다. 단순 리뷰 수가 품질로 오해되지 않도록 UI 라벨을 명확히 한다.

### 10.5 신규순

도락 등록일이 아니라 실제 개업일 또는 공개 확인일을 사용한다. 개업일을 알 수 없는 지점은 신규 음식점으로 오인시키지 않는다.

## 11. 지도 검색

### 11.1 화면 영역 검색

- 클라이언트는 지도 bounding box와 zoom level을 보낸다.
- 서버는 `geo_bounding_box`로 후보를 제한한다.
- 지나치게 큰 영역은 결과 대신 지역 집계 또는 확대 요청을 반환한다.
- 날짜변경선 등 일반 국내 범위 밖 예외도 입력 검증한다.

### 11.2 반경 검색

현재 위치 주변은 `geo_distance` 쿼리를 사용한다. 사용자가 선택하지 않은 임의 반경을 무한 확대하지 않는다.

### 11.3 군집화

낮은 확대 수준에서는 개별 지점을 모두 내려보내지 않는다.

서버 응답 후보:

- geotile grid 군집
- 군집 중심과 결과 수
- 군집 내 대표 카테고리와 점수 분포
- 사용자가 확대할 다음 경계

높은 확대 수준에서만 개별 마커를 반환한다.

### 11.4 지도와 목록 일관성

- 동일 필터와 검색 세션을 사용한다.
- 목록 선택 시 마커를 강조한다.
- 지도 이동이 자동으로 기존 검색 조건을 지우지 않는다.
- `이 지역 다시 검색` 전후 상태를 명확히 한다.
- 현재 화면 밖의 상단 검색 결과를 지도에 억지로 포함하지 않는다.

### 11.5 위치 개인정보

- 검색 요청의 정밀 위치를 일반 분석 로그에 그대로 저장하지 않는다.
- 세션 내 검색에는 필요 시 사용하고 장기 분석은 격자·행정구역으로 낮춘다.
- 점주에게 개별 사용자 위치를 제공하지 않는다.

## 12. 자동완성

### 12.1 결과 유형

- 정확·인기 음식점
- 지역·역·상권
- 음식 장르
- 메뉴
- 최근 검색, 사용자 기기 또는 계정 설정에 따라

### 12.2 랭킹

- 접두 일치
- 정확 상호
- 지역 맥락
- 제한된 전체 검색 빈도
- 사용자의 최근 검색 및 저장, 개인화 동의 시
- 폐업 상태와 데이터 신뢰도

자동완성 인기도는 조작 방지를 위해 고유 사용자, 시간 감쇠, 봇 필터를 적용한다.

### 12.3 개인정보

- 다른 사용자의 검색어를 원문 인기 추천으로 노출하지 않는다.
- 소수 사용자만 입력한 장문 쿼리는 추천 후보에서 제외한다.
- 최근 검색은 사용자가 삭제하고 저장을 끌 수 있어야 한다.

## 13. 오탈자와 결과 없음

### 13.1 오탈자

- 짧은 상호에는 공격적인 fuzzy를 제한한다.
- 편집거리와 키보드 인접성을 함께 평가한다.
- 지역·장르 사전의 높은 확신 교정은 제안으로 표시한다.
- 교정 결과와 원문 검색을 비교 가능하게 한다.

### 13.2 결과 없음 전략

순서:

1. 철자 교정 제안
2. 너무 강한 필터 완화 제안
3. 인접 지역 확장
4. 하위 장르를 상위 장르로 확장
5. 영업 중 또는 예약 조건 해제 제안
6. 음식점 신규 제보

사용자 모르게 거리와 필터를 크게 확장하지 않는다. 확장 여부를 UI에서 설명한다.

## 14. 필터

### 14.1 기본 필터

- 지역과 거리
- 음식 장르
- 가격대
- 현재 또는 특정 시각 영업
- 예약 가능
- 도락 점수 구간
- 방문 인증 리뷰 수 조건
- 주차, 포장, 배달
- 혼밥, 단체, 룸
- 접근성
- 채식 및 종교식 옵션
- 아동·반려동물 정책

### 14.2 출처와 확신

시설 정보는 다음 출처 우선순위를 고려한다.

- 점주 공식 확인
- 운영자 검수
- 신뢰할 수 있는 파트너
- 다수의 최근 사용자 제보
- 리뷰 텍스트 추론

낮은 신뢰도의 속성을 확정 필터에 사용하면 결과 누락이 발생할 수 있다. 속성별 최소 확신 기준을 둔다.

### 14.3 Facet

검색 결과 집계는 현재 필터가 적용된 후보 안에서 계산한다. 다중 선택 필터의 self-filtering 동작을 제품별로 일관되게 정의한다.

## 15. 광고 슬롯

### 15.1 분리 구조

```text
natural search request ──→ organic candidates

ad request ──────────────→ eligible sponsored candidates
                                  ↓
response composer ── clearly labeled placement
```

광고 서비스는 자연 검색 내부 점수를 수정하지 않는다.

### 15.2 광고 자격

- 검색 의도와 관련 있음
- 영업 상태 및 지역 조건 충족
- 점주 권한과 광고 계약 유효
- 정책 위반 또는 사칭 상태가 아님
- 사용자가 선택한 강한 필터를 위반하지 않음

### 15.3 표시

- `광고` 라벨
- 자연 검색과 구분되는 슬롯
- 동일 지점의 광고·자연 결과 중복 처리
- 광고 때문에 자연 결과 수가 줄지 않게 함

### 15.4 금지

- 광고비로 도락 점수순 상승
- 공식 랭킹 내 광고 삽입
- 광고임을 숨긴 추천 배지
- 사용자가 거리순을 선택했는데 광고를 거리순처럼 혼합

## 16. 개인화 검색

개인화는 관련도순의 제한된 보조 재정렬로 사용한다.

후보 신호:

- 선호 장르와 가격대
- 저장·방문 이력
- 팔로우 리뷰어
- 접근성·식이 설정
- 사용자가 선택한 제외 조건

원칙:

- 정확 상호 검색을 개인화로 바꾸지 않는다.
- 전체 공개 점수와 개인 취향 일치를 구분한다.
- 민감한 방문 이력을 설명 문구에 노출하지 않는다.
- 개인화 끄기와 기록 삭제를 제공한다.
- 광고 개인화는 별도 동의와 정책을 적용한다.

## 17. 의미 기반 검색

벡터 또는 생성형 검색은 v1 필수요소가 아니다. 한글 상호·지역·장르·메뉴의 구조화 검색 품질을 먼저 확보한다.

향후 후보:

- 자연어 조건에서 구조화 필터 추출
- 리뷰와 음식점 설명 임베딩
- 키워드와 벡터의 hybrid 검색
- 검색 결과 요약

도입 조건:

- 평가셋에서 기존 검색 대비 명확한 개선
- 광고와 자연 검색 분리 유지
- 사용자 리뷰의 외부 모델 전송 정책 검토
- 환각된 메뉴·시설 생성 방지
- 결과 근거와 원문 연결
- 비용·지연 목표 충족

## 18. 색인 동기화

### 18.1 증분 색인

1. PostgreSQL 트랜잭션에서 원장 변경과 outbox 이벤트 기록
2. 이벤트 게시 작업이 검색 큐에 전달
3. 문서 빌더가 최신 원장 상태 조회
4. 엔터티 버전과 문서 버전 비교
5. 최신 문서 upsert 또는 폐업 상태 반영
6. 처리 체크포인트 기록

이벤트 payload 전체를 그대로 색인하지 않고 최신 원장을 읽어 문서를 만든다.

### 18.2 전체 재색인

```text
branches-v3-build-20260903
  ↓ validation
branches-read alias switch
  ↓ observation window
old index retirement
```

- 새 schema 버전의 별도 인덱스 생성
- 일정한 입력 기준시각 사용
- 샤드별 재시작 가능한 bulk 색인
- 문서 수와 샘플 내용 검증
- 대표 쿼리 회귀 테스트
- alias 원자 전환
- 되돌리기 기간 후 구 인덱스 삭제

### 18.3 삭제와 개인정보

- 공개 콘텐츠 삭제 이벤트를 우선 처리한다.
- 정기 대조로 고아 문서를 찾는다.
- 계정 삭제 후 리뷰어·리스트 인덱스에서 개인 식별 필드를 제거한다.
- 검색 스냅샷과 백업의 보존기간을 정의한다.

## 19. 장애와 기능 저하

### 19.1 OpenSearch 장애

- 정확 branch ID 상세 조회는 PostgreSQL 경로로 유지한다.
- 최근 본 음식점과 저장 목록은 검색 없이 제공한다.
- 검색 화면은 명확한 일시 장애 상태를 표시한다.
- PostgreSQL에 광범위한 `ILIKE` 검색을 자동 전가해 원장 장애를 유발하지 않는다.

### 19.2 지연된 색인

- 음식점 상세는 원장 최신 상태를 사용한다.
- 폐업·법적 차단과 같은 긴급 상태는 API 응답 후처리 또는 별도 denylist로 즉시 반영할 수 있다.
- 지연 시간 메트릭이 기준을 넘으면 경보한다.

### 19.3 지도 공급자 장애

- 목록 검색은 유지한다.
- 외부 지도 타일 오류와 음식점 검색 오류를 구분한다.
- 좌표와 도락 원장은 지도 공급자 장애와 무관하게 유지한다.

## 20. 페이지네이션과 일관성

- 얕은 검색은 `search_after` 기반 cursor를 사용한다.
- cursor에는 정렬값, 문서 ID, 검색 schema 버전, 만료를 서명해 포함한다.
- 사용자에게 임의의 페이지 번호를 제공해야 하는 SEO 목록은 제한된 범위에서 별도 전략을 사용한다.
- 긴 세션의 일관성이 중요하면 Point in Time 사용을 검토한다.
- cursor 재사용 시 쿼리와 필터 해시가 다르면 거부한다.

## 22. 품질 평가

### 22.1 오프라인 평가셋

평가셋은 다음 쿼리 유형을 포함한다.

- 정확 상호
- 지점 상호
- 초성
- 오탈자
- 지역 + 장르
- 메뉴
- 속성
- 현재 영업
- 결과가 없어야 하는 쿼리
- 폐업·이전 상호
- 영문·일문·중문 표기

평가자는 결과의 관련성을 다단계 등급으로 표시하고 지역과 장르 지식을 기록한다.

### 22.2 지표

- NDCG@K
- MRR
- Recall@K
- 정확 상호 Top-1 성공률
- 자동완성 선택률
- 결과 없음 비율
- 검색어 재작성률
- 결과 클릭 후 즉시 복귀율
- 검색 → 저장·길찾기·예약 전환
- p50, p95, p99 지연

전환율만 최적화하면 자극적이고 유명한 결과에 편향될 수 있으므로 관련성 판단과 함께 본다.

### 22.3 온라인 실험

- 실험 전 성공·가드레일 지표 정의
- 광고 수익을 자연 검색 품질 성공 지표로 사용하지 않음
- 지역·장르별 영향 분석
- 신규·소규모 음식점 노출 점검
- 실험 종료 후 장기 효과 확인

- 정확·ngram·초성·별칭 다중 필드
- 지역·장르·메뉴 검색
- bounding box와 반경 검색
- 기본 필터와 정렬
- 자동완성
- 폐업·이전 처리
- outbox 기반 증분 색인
- alias 기반 전체 재색인
- 자연 검색과 광고 응답 분리
- 평가셋과 회귀 테스트

### 제외

- 생성형 답변형 검색
- 사용자 리뷰 전체 벡터 색인
- 복잡한 실시간 학습 랭킹
- 광고와 자연 결과의 단일 점수 경매
- 사용자 정밀 위치 장기 저장
- 외부 지도 장소 ID를 원장으로 사용

## 26. 미결정 사항

- OpenSearch 형태소 분석 설정과 사용자 사전
- 자동완성용 n-gram 범위
- 검색 결과의 기본 반경과 지도 최대 경계
- 관련도에서 공개 점수의 최대 영향 범위
- 인기도 반감기와 포화 함수
- 속성 태그의 최소 출처 신뢰도
- 광고 슬롯 수와 중복 처리
- Point in Time 기반 페이지네이션 적용 범위
- 다국어 별도 인덱스 또는 단일 인덱스 전략
- 의미 기반 검색 도입 기준
- 점주가 검색 별칭을 제안하는 운영 절차
