# 도락 운영 체계 설계

> 상태: 초안 v0.1  
> 범위: 음식점 데이터, 콘텐츠, 점주 인증, 예약·결제 지원, 개인정보 요청, 장애 대응  
> 원칙: 운영자 개인의 기억이 아니라 큐, 정책, 증거, 감사 기록으로 운영한다.  
> 연관 문서: [DATA_MODEL.md](../architecture/DATA_MODEL.md), [MODERATION_POLICY.md](../policies/MODERATION_POLICY.md), [RESERVATION_SYSTEM.md](../features/RESERVATION_SYSTEM.md), [PRIVACY_SECURITY.md](../policies/PRIVACY_SECURITY.md)

## 1. 목적

도락은 데이터와 신뢰가 제품 자체인 서비스다. 앱 화면이 정상이어도 음식점 중복, 허위 리뷰, 잘못된 영업 상태, 점주 사칭, 예약·환불 불일치가 쌓이면 제품은 실패한다.

이 문서는 다음을 정한다.

- 어떤 운영 업무가 존재하고 어느 팀이 책임지는가
- 사건이 어떻게 접수, 분류, 배정, 결정, 통지, 종료되는가
- 운영자가 무엇을 볼 수 있고 무엇을 변경할 수 있는가
- 긴급도와 서비스 목표를 어떻게 정하는가
- 자동화와 사람 판단의 경계를 어디에 두는가
- 데이터 수정과 제재를 어떻게 재현하고 되돌릴 수 있는가
- 장애, 금전 불일치, 안전 신고를 어떻게 지휘하는가

## 2. 운영 원칙

### 2.1 직접 데이터베이스 수정 금지

운영자에게 DB 콘솔을 일상 도구로 제공하지 않는다. 모든 변경은 검증된 명령, 권한 확인, 영향 미리보기, 감사 이벤트를 거친다.

긴급 수동 SQL이 불가피했던 경우에는 사고로 간주하고 다음을 남긴다.

- 실행 승인자와 실행자
- 변경 대상과 범위
- 실행 쿼리의 안전한 보관
- 변경 전후 검증
- 정식 운영 도구로 대체할 후속 작업

### 2.2 한 사건에 하나의 책임자

각 사건은 단일 owner와 현재 응답 기한을 가진다. 여러 팀이 협업하더라도 누가 다음 행동을 해야 하는지 모호하지 않게 한다.

### 2.3 정책과 사실을 분리한다

운영자는 사실과 증거를 기록하고, 정책 버전에 따라 결정을 내린다. 개인적 호감, 매출 기여, 광고 계약이 판단 기준에 들어가지 않는다.

### 2.4 최소 권한과 목적 제한

업무 큐의 모든 사건을 모든 운영자가 볼 수 없게 한다. 예약 연락처, 영수증, 위치 증빙, 결제 기록은 배정 사건에서 필요한 최소 범위만 해제한다.

### 2.5 되돌릴 수 있는 조치를 우선한다

불확실한 초기 대응은 노출 제한, 기능 잠금, 지급 보류처럼 복구 가능한 조치를 사용한다. 영구 삭제나 계정 폐쇄는 증거와 승인 기준을 더 높인다.

### 2.6 결정과 집행을 구분한다

고위험 사건은 한 명이 증거를 보고 결정과 집행을 모두 하지 못하게 할 수 있다. 환불 조정, 점주 소유권 이전, 대규모 지점 병합, 영구 제재는 이중 승인을 적용한다.

### 2.7 사용자에게 상태를 알려준다

내부 세부 탐지 규칙이나 타인의 개인정보를 밝히지 않으면서 접수, 추가 정보 요청, 결정, 이의 제기 방법을 알려준다.

## 3. 운영 조직

초기에는 한 사람이 여러 역할을 겸할 수 있으나 시스템 권한과 책임은 분리해 설계한다.

| 기능 | 주요 책임 |
|---|---|
| Data Operations | 음식점 생성·병합·폐업·주소·카테고리·출처 품질 |
| Trust & Safety | 리뷰·사진·프로필·신고·부정행위·제재·이의 제기 |
| Merchant Operations | 점주 인증·권한·공식 정보·교육·분쟁 |
| Reservation Support | 예약 변경·취소·노쇼·알림·지점 운영 지원 |
| Payment Operations | 결제·환불·정산 불일치와 공급자 조정 |
| Privacy Operations | 열람·정정·삭제·동의·위치정보 요청 |
| Customer Support | 일반 문의, 1차 분류, 사용자 소통 |
| Site Reliability | 장애 지휘, 복구, 용량, 변경 관리 |
| Security Response | 계정 탈취, 데이터 침해, 내부 오용 |
| Legal & Policy | 정책 해석, 법적 요청, 고위험 분쟁 |

초기 최소 조직에서는 다음 겸임을 허용할 수 있다.

- Data Ops + Merchant Ops
- Reservation Support + Payment Ops
- Customer Support + 1차 Trust & Safety triage

다만 승인 권한까지 같은 사람에게 무제한 부여하지 않는다.

### 4.3 민감 작업 통제

| 작업 | 통제 |
|---|---|
| 예약 연락처 전체 보기 | 사건 배정 + 사유 + 시간 제한 |
| 영수증 원본 보기 | Trust/Privacy 역할 + 워터마크 |
| 점주 소유권 이전 | 별도 제안자·승인자 |
| 고액 수동 환불 | 금액 임계치별 이중 승인 |
| 영구 계정 제재 | 근거 코드 + 상위 검토 가능 |
| 대량 지점 병합 | 영향 미리보기 + 승인 + 복구 계획 |
| 개인정보 내보내기 | 요청자 신원 재확인 + 제한 URL |
| 감사 로그 조회 | 감사 역할 + 조회 자체 감사 |

### 4.4 임시 권한

긴급 권한 상승은 다음을 요구한다.

- 사건 또는 장애 ID
- 필요한 권한과 대상 범위
- 자동 만료 시각
- 승인자
- 사용 내역 사후 검토

공유 운영자 계정을 금지한다.

## 5. 공통 사건 모델

### 5.1 `operations_case`

```text
id
case_type
source
subject_type and subject_id
reporter/initiator reference
priority
status
assigned_team
assigned_operator
policy_version
due_at
sensitivity_class

```

### 5.2 상태 머신

```text
new -> triaged -> assigned -> investigating
                              -> awaiting_user
                              -> awaiting_merchant
                              -> awaiting_partner
                              -> awaiting_approval
                              -> decided -> executing -> resolved -> closed

any non-terminal -> duplicate
any non-terminal -> invalid
closed -> reopened
```

상태만 보고 업무가 멈추지 않게 `next_action`, `next_actor`, `due_at`을 함께 기록한다.

### 5.3 사건 유형

```text
branch_data_correction

owner_claim

content_report

payment_mismatch

```

### 5.4 우선순위

| 등급 | 정의 | 예 |
|---|---|---|
| P0 | 즉각적인 광범위 피해 또는 진행 중 안전·보안 사고 | 데이터 침해, 이중 결제 확산, 대규모 예약 중복 |
| P1 | 시간 민감한 중대한 개인 피해 | 오늘 예약 불일치, 계정 탈취, 실주소 노출 |
| P2 | 일반 사건 중 금전·평판·권한 영향 | 환불 지연, 점주 인증 분쟁, 명예훼손 신고 |
| P3 | 비긴급 정확성·사용 문의 | 메뉴 수정, 일반 중복 제보, 기능 문의 |
| P4 | 개선 요청·백로그 | 분류 개선, UI 제안 |

접수 채널의 감정적 표현만으로 우선순위를 높이지 않고 피해 범위, 긴급성, 가역성, 취약 사용자를 고려한다.

### 5.5 감사 이벤트

사건의 모든 조회·변경 중 민감 행동은 다음을 남긴다.

```text
actor
role and authority context
case id
action
target
reason code
safe before/after diff
request id
timestamp
```

## 6. 접수와 분류

### 6.1 접수 채널

- 앱·웹 신고
- 점주 콘솔
- 고객지원 문의
- 자동 탐지
- 파트너 웹훅·지원 채널
- 보안 신고
- 개인정보 요청 채널
- 법적 문서 접수
- 내부 모니터링과 장애 경보

### 6.2 접수 시 검증

- 중복 사건이 있는지
- 즉각 숨김이나 기능 차단이 필요한지
- 요청자 신원을 추가 확인해야 하는지
- 개인정보가 불필요하게 첨부되었는지
- 잘못된 팀으로 유입되었는지
- 응답 시한이 법률·거래 조건상 정해져 있는지

### 6.3 자동 분류의 한계

자동 분류는 큐, 우선순위 후보, 유사 사건을 추천할 수 있다. 다음은 사람 확인 없이 자동 확정하지 않는다.

- 명예훼손이나 불법성의 최종 판단
- 점주 소유권 분쟁 승자
- 영구 계정 정지
- 고액 환불 조정
- 개인정보 삭제 예외 적용
- 법적 요청의 유효성

### 6.4 중복 사건

원 사건에 연결하되 신고자별 통지와 증거 출처는 보존한다. 신고 수가 많다는 사실만으로 위반을 확정하지 않는다.

## 7. 음식점 데이터 운영

### 7.1 데이터 업무 유형

- 신규 지점 후보 승인
- 중복 병합
- 잘못된 병합 분리
- 이전·폐업·임시 휴업
- 브랜드·지점 관계
- 주소와 좌표 보정
- 카테고리와 대표 장르
- 영업시간·메뉴 충돌
- 공공·점주·사용자 출처 충돌

### 7.2 출처 우선순위는 절대 순위가 아니다

필드와 상황별 신뢰도를 평가한다.

| 사실 | 강한 출처 예 |
|---|---|
| 법적 영업 상태 | 현재 공공 인허가 + 확인된 운영 정보 |
| 오늘 임시 휴무 | 인증 점주 또는 다수의 최근 현장 신호 |
| 대표 메뉴 | 점주 공식 메뉴 + 사용자 최근 사진 교차 확인 |
| 입구 좌표 | 현장 검증 좌표 + 지도 기하 |
| 상호 표기 | 공식 간판·점주·인허가 정보의 문맥별 조합 |

오래된 공식 출처가 최근 현장 사실보다 항상 우선하는 구조를 피한다.

### 7.3 데이터 assertion 처리

```text
candidate created
 -> auto-accepted if low-risk and high-confidence
 -> queued for review
 -> accepted / rejected / superseded / expired
```

판단 입력:

- 출처 유형과 과거 정확도
- 관측 시각
- 기존 값과 차이 크기
- 다른 독립 출처의 일치
- 소비자·예약에 미치는 영향
- 점주 인증 상태
- 조작 위험 신호

### 7.4 중복 병합

병합 전 영향 보고서:

```text
reviews and photos
saved lists
visits and verification
owner claims and permissions
active reservations
search redirects and slugs
external mappings
score history
moderation cases
```

진행 순서:

1. 기준 지점 후보와 병합 대상을 선택한다.
2. 필드별 승자와 충돌을 미리 보여 준다.
3. 활성 예약과 점주 권한이 있으면 상위 승인을 요구한다.
4. redirect와 이전 관계를 만든다.
5. 관계를 배치 단위로 이전한다.
6. 검색·점수·캐시를 재계산한다.
7. 샘플과 불변식을 검증한다.
8. 복구 가능한 병합 스냅샷을 보존한다.

### 7.5 잘못된 병합 분리

병합 후 생긴 새 데이터 때문에 단순 롤백하지 않는다. 병합 전 스냅샷과 이후 변경을 비교해 각 리뷰, 예약, 사진, 점주 권한의 귀속 계획을 만든다.

### 7.6 폐업과 이전

- 폐업은 페이지 삭제가 아니라 영업 상태 변경이다.
- 리뷰와 과거 정보는 정책에 따라 유지한다.
- 이전 후 정체성이 이어지면 이전 관계를 표시한다.
- 완전히 다른 업종·사업자가 같은 주소를 쓰면 새 지점을 만든다.
- 활성 예약이 있으면 폐업 상태 공개 전 예약 운영 사건을 생성한다.

### 7.7 품질 샘플링

자동 승인 데이터도 지역·출처·필드별로 정기 표본 검수한다. 정확도 평균 하나만 보지 않고 다음을 분리한다.

- 존재 여부
- 좌표
- 영업 상태
- 상호
- 카테고리
- 영업시간
- 예약 가능 표시

## 8. 콘텐츠 운영

세부 정책은 [MODERATION_POLICY.md](../policies/MODERATION_POLICY.md)를 따른다.

### 8.1 처리 순서

1. 대상 콘텐츠와 현재 공개 상태를 고정한다.
2. 신고 사유를 표준 코드로 정규화한다.
3. 즉시 피해가 있으면 가역적 임시 조치를 검토한다.
4. 작성 맥락, 수정 이력, 방문·이해관계 공개를 확인한다.
5. 필요한 최소 증거만 요청한다.
6. 정책 버전에 따라 결정한다.
7. 콘텐츠·계정 조치를 각각 집행한다.
8. 관련 당사자에게 허용 범위의 결과를 통지한다.
9. 이의 제기 가능 기간과 방법을 제공한다.

### 8.2 점주 이의 제기

점주가 불쾌하다는 이유만으로 리뷰를 숨기지 않는다. 다음을 구분한다.

- 사실관계 반박: 답글 또는 수정 요청
- 정책 위반: 콘텐츠 신고
- 작성자 미방문 의심: 방문 무결성 검토
- 명백한 다른 지점 리뷰: 귀속 수정
- 법적 주장: Legal/Policy 큐

### 8.3 증거 접근

영수증, 예약, 위치 증빙을 점주에게 원본으로 전달하지 않는다. 운영자는 `인증됨`, `불충분`, `취소됨` 같은 판정 결과만 필요한 범위에서 설명한다.

### 8.4 제재 누적

경고 횟수만 세지 않는다. 위반 유형, 의도, 반복성, 피해, 계정 탈취 가능성, 정책 교육 여부를 함께 본다.

### 8.5 품질 관리

- 리뷰어 간 일치율
- 뒤집힌 결정 비율
- 정책 사유별 처리 시간
- 특정 점주·광고 상태에 따른 편향
- 특정 언어·지역·장애 사용자에 대한 차이
- 자동 탐지의 정밀도와 재현율

## 9. 점주 운영

### 9.1 지점 claim 흐름

```text
draft -> submitted -> identity/business verification
                  -> conflict check
                  -> approved
                  -> rejected
                  -> disputed
approved -> revoked / transferred
```

### 9.2 검증 증거

- 사업자·영업 관련 서류
- 대표자 또는 위임 관계
- 지점 연락 수단 확인
- 기존 점주 계정과의 충돌
- 공식 도메인 또는 계약 정보

서류는 필요한 필드만 추출하고 원본 보존기간을 최소화한다.

### 9.3 소유권 충돌

- 새 신청으로 기존 소유자를 자동 해제하지 않는다.
- 양측 권한을 임시 제한할 필요가 있는지 평가한다.
- 지점 운영에 필요한 예약 담당 접근은 별도로 연속성을 확보한다.
- 사실과 증거를 양측에 과도하게 공개하지 않는다.
- 최종 이전에는 이중 승인과 통지를 적용한다.

### 9.4 점주 교육

첫 승인 시 다음을 안내하고 확인한다.

- 리뷰 삭제를 구매할 수 없다는 원칙
- 답글 정책
- 직원·가족의 리뷰 금지 또는 이해관계 공개
- 공식 정보와 광고의 구분
- 예약 연락처의 목적 외 사용 금지
- 예약 취소·노쇼 처리 기준
- 계정 공유 금지와 구성원 초대

### 9.5 점주 품질 지표

- 공식 정보 최신성
- 정보 수정 승인 정확도
- 예약 응답 시간
- 점주 취소율
- 노쇼 판정 정정률
- 사용자 연락처 접근 이상
- 리뷰 신고 승인율의 비정상 패턴

낮은 성과를 검색 자연 순위에 비공개로 직접 반영하지 않는다. 예약 가능성이나 공식 정보 신뢰도처럼 관련 있는 표시 신호로만 사용한다.

## 10. 예약·결제 운영

세부 상태는 [RESERVATION_SYSTEM.md](../features/RESERVATION_SYSTEM.md)를 따른다.

### 10.1 예약 사건 큐

- 오늘/임박 예약 우선
- 점주 미응답
- 중복 자원 배정
- 변경안 응답 대기
- 점주 취소
- 노쇼 분쟁
- 외부 채널 동기화 실패
- 거래 알림 실패

### 10.2 결제 조정 큐

- 성공 결제에 대응 예약 없음
- 예약 취소 후 환불 없음
- 공급자와 내부 금액 불일치
- 중복 승인·중복 환불
- 장기 `processing` 또는 `unknown`
- chargeback 또는 지급 분쟁

### 10.3 수동 조정 원칙

- 예약 상태와 결제 상태를 별도로 확인한다.
- 공급자 대시보드 화면만 믿지 않고 API/원장 참조를 기록한다.
- 환불을 재시도하기 전에 기존 provider reference를 조회한다.
- 조정 금액은 원 계산과 차이를 표시한다.
- 사용자의 새 결제를 유도하기 전에 이전 결제 상태를 확정한다.

### 10.4 임박 예약 연락

지원팀이 사용자를 대신해 예약 조건을 변경하지 않는다. 점주·사용자 양쪽의 동의가 필요한 변경은 제안 상태로 처리한다.

### 10.5 중복 예약 사고

1. 추가 확정을 즉시 차단한다.
2. 영향 예약과 자원을 고정한다.
3. 지점에 사실 확인과 수용 가능한 대안을 요청한다.
4. 사용자별 연락·대안·환불 상태를 추적한다.
5. 책임 채널과 원인을 확인한다.
6. 재고 불변식과 연동을 수정한다.
7. 사고 검토와 점주/파트너 후속 조치를 완료한다.

## 11. 개인정보 요청 운영

### 11.1 요청 유형

- 처리·보유 정보 열람
- 정정
- 삭제·계정 종료
- 처리 정지 또는 동의 철회
- 데이터 내보내기
- 위치정보 관련 요청
- 자동화된 결정에 대한 문의·이의

### 11.2 처리 흐름

1. 요청 채널과 범위를 확인한다.
2. 위험에 맞는 신원 확인을 한다.
3. 관련 시스템과 법정 보관 예외를 찾는다.
4. 제3자 정보와 내부 보안 신호를 분리한다.
5. 실행 계획을 만들고 승인한다.
6. 내보내기·정정·삭제를 실행한다.
7. 각 시스템 결과를 검증한다.
8. 사용자에게 결과와 제한 사유를 통지한다.
9. 요청 처리 증거는 내용과 분리해 보관한다.

### 11.3 삭제가 곧 행 삭제는 아니다

- 공개 프로필과 리뷰 표시를 분리한다.
- 법정 거래 기록은 제한 보관할 수 있다.
- 부정행위 방지에 필요한 최소 토큰은 별도 근거와 기간이 필요하다.
- 백업은 즉시 개별 삭제가 어려울 수 있으므로 복원 시 재삭제 절차를 둔다.
- 검색 색인, 캐시, 분석 파생 데이터까지 전파를 확인한다.

### 11.4 개인정보 사건과 일반 지원 분리

일반 상담원이 신분증이나 전체 데이터 내보내기를 처리하지 않는다. 전용 보안 채널과 Privacy 역할로 넘긴다.

## 12. 고객지원

### 12.1 지원 단계

| 단계 | 범위 |
|---|---|
| L0 | 도움말, 앱 내 상태, 자동 안내 |
| L1 | 일반 문의, 계정 기본 문제, 사건 접수 |
| L2 | 데이터·예약·점주·콘텐츠 전문 큐 |
| L3 | 엔지니어링, 보안, 정책, 법률, 공급자 |

### 12.2 상담원 도구

- 사용자 화면의 안전한 미리보기
- 최근 요청과 거래 상태 요약
- 마스킹된 연락처
- 사건 생성과 전문 큐 전달
- 승인된 템플릿 답변
- 앱 버전·플랫폼·요청 ID 확인

로그인 대행, 사용자 비밀번호 확인, 임의 리뷰 편집 기능을 제공하지 않는다.

### 12.3 사용자 인증

계정·예약 문의에서 이름과 전화번호 일부만 물어보는 단순 인증에 의존하지 않는다. 로그인 세션, 예약 확인 수단, 위험 기반 추가 인증을 사용한다.

### 12.4 템플릿

템플릿은 일관성을 돕지만 결정을 대신하지 않는다. 다음 변수는 자동 삽입한다.

```text
case id
current status
action taken
next required action
due date or expected update
appeal/support path
```

내부 정책 문구를 그대로 붙여 사용자를 탓하는 표현을 피한다.

## 14. 교대와 인수인계

### 14.1 사건 메모 형식

```text
현재 알려진 사실
확인되지 않은 주장
사용자/점주 영향
이미 수행한 조치
남은 위험
다음 행동과 담당자
기한
관련 로그·증거의 안전한 참조
```

### 14.2 고위험 큐 교대

- 임박 예약과 결제 사건을 구두/동기 인계한다.
- P0/P1은 owner가 확인했다는 acknowledgment를 남긴다.
- 비밀이나 개인정보를 채팅에 복사하지 않고 사건 링크를 사용한다.
- 교대 중 사건 담당자가 비어 있지 않게 한다.

### 14.3 휴일 운영

예약 서비스는 음식점 영업일에 맞춰 야간·주말 사건이 생긴다. 일반 사무시간 지원과 별개로 온콜 범위와 점주 긴급 채널을 정한다.

## 15. 장애 대응

### 15.1 장애 등급

| 등급 | 기준 |
|---|---|
| SEV-0 | 안전·보안·대규모 금전 피해 진행 중 |
| SEV-1 | 예약 핵심 기능 또는 주요 지역 전체 장애 |
| SEV-2 | 일부 기능·파트너·지역의 심각한 기능 저하 |
| SEV-3 | 제한적 오류, 우회 가능 |

### 15.2 지휘 역할

```text
Incident Commander: 우선순위와 의사결정
Technical Lead: 원인 분석과 복구
Operations Lead: 사용자·점주 영향 처리
Communications Lead: 상태 공지와 내부 업데이트
Scribe: 타임라인과 결정 기록
Security/Privacy Lead: 해당 사건일 때 참여
```

한 사람이 초기에 여러 역할을 맡더라도 역할 이름으로 행동을 구분한다.

### 15.3 초기 대응

1. 사건 등급과 지휘자를 선언한다.
2. 영향 범위와 시작 시각을 추정한다.
3. 최근 변경과 외부 의존성을 확인한다.
4. 피해 확대를 막는 기능 플래그·채널 차단을 검토한다.
5. 예약·결제·개인정보 불변식을 확인한다.
6. 내부 업데이트 주기를 정한다.
7. 사용자 공지 필요성을 결정한다.

### 15.4 기능별 안전 저하

| 장애 | 유지 | 차단·표시 |
|---|---|---|
| 검색 엔진 | 인기/근처 제한 fallback 가능 | 복잡 필터·정렬 제한 |
| 평점 배치 | 마지막 승인 점수 | 새 점수 발행 중단 |
| 미디어 처리 | 텍스트·검색 | 새 이미지 처리 지연 표시 |
| 예약 엔진 | 음식점 상세·전화 | 실시간 예약 확정 차단 |
| 결제사 | 무결제 탐색 | 신규 유료 예약 차단 |
| 알림사 | 앱 내 예약 상태 | 채널 지연 안내, 대체 채널 |
| 점주 콘솔 | 소비자 확정 정책에 따라 | 수동 변경 제한, 지원 채널 |

### 15.5 사고 후 검토

비난이 아니라 시스템 개선을 목적으로 다음을 기록한다.

- 실제 타임라인
- 탐지한 신호와 놓친 신호
- 사용자·점주·금전·데이터 영향
- 잘된 방어와 실패한 방어
- 근본 원인과 기여 요인
- 즉시·중기·구조적 후속 작업
- 각 작업의 owner와 완료 조건

`운영자 실수`를 근본 원인으로 끝내지 않는다. 왜 한 번의 실수가 큰 피해로 이어졌는지 통제 구조를 분석한다.

## 16. 재해 복구와 비즈니스 연속성

### 16.1 우선순위

1. 인증과 권한 보호
2. 예약·결제 원장 무결성
3. 음식점 핵심 데이터와 리뷰 원본
4. 점수·검색·분석 파생 데이터 재생성

### 16.2 복구 기준

구체적 RPO/RTO는 기술 스택과 비용 검증 후 확정하되 시스템별로 별도 설정한다.

| 시스템 | 데이터 손실 허용 방향 | 복구 방향 |
|---|---|---|
| 예약·결제 | 거의 0에 가깝게 | 최우선 |
| 계정·권한 | 거의 0에 가깝게 | 최우선 |
| 리뷰 원본 | 낮게 | 우선 |
| 검색 색인 | 재생성 가능 | 점진 복구 |
| 분석 집계 | 재처리 가능 | 후순위 |

### 16.3 복구 훈련

- 데이터베이스 시점 복구
- 잘못된 지점 대량 병합 복원 계획
- 검색 전체 재색인
- 큐와 outbox 재생
- 결제 공급자와 상태 재조정
- 비밀·키 회전
- 리전 또는 계정 장애 대응

백업 성공 로그만 보지 않고 실제 복원과 애플리케이션 검증을 수행한다.

## 17. 변경 관리

### 17.1 변경 위험 등급

| 등급 | 예 | 통제 |
|---|---|---|
| Low | 문구, 비핵심 UI | 일반 리뷰·자동 배포 |
| Medium | 검색 필터, 점주 편집 | 테스트·단계 배포 |
| High | 평점 모델, 권한, 예약 상태 | 승인·shadow/canary·복구 계획 |
| Critical | 결제, 개인정보 파기, 대량 병합 | 이중 승인·훈련된 runbook |

### 17.2 변경 금지 시간

연휴·인기 예약 오픈·대규모 이벤트 전에는 예약과 결제의 고위험 변경을 제한한다. 긴급 보안 패치는 예외지만 지휘 체계 아래 수행한다.

### 17.3 기능 플래그

- 사용자·지점·지역·앱 버전 범위가 명확해야 한다.
- 플래그 owner와 만료일을 둔다.
- off가 데이터 정합성을 깨지 않는지 검증한다.
- 긴급 차단 플래그는 권한과 감사 로그를 강화한다.
- 오래된 플래그를 분기별 제거한다.

## 18. 운영 자동화

### 18.1 자동화 적합 업무

- 중복 후보 생성
- 명백한 데이터 형식 정규화
- 사건 라우팅과 기한 계산
- 결제·예약 불일치 탐지
- 만료 hold 해제
- 정책 기반 거래 알림
- 증거 보존기간 만료 처리
- 샘플링과 품질 대시보드

### 18.2 사람 승인 필요 업무

- 정체성이 불분명한 지점 병합
- 영구 제재
- 점주 소유권 이전
- 고액 환불 조정
- 표현의 맥락이 중요한 콘텐츠 제거
- 법적·개인정보 예외 판단

### 18.3 자동화 안전장치

```text
dry-run
affected-count threshold
rate limit
scope allowlist
idempotency
checkpoint
kill switch
audit event
sample verification
rollback or compensating action
```

대량 작업이 예상보다 많은 대상을 찾으면 자동 중지한다.

## 19. 운영 도구 UX

### 19.1 사건 화면

```text
상단: 유형, 상태, 우선순위, owner, 기한
좌측: 안전한 대상 미리보기와 관계
중앙: 타임라인, 증거, 메시지
우측: 정책 근거, 권장 다음 행동
하단: 권한 있는 명령과 영향 미리보기
```

### 19.2 위험한 버튼

- 구체적인 동사와 대상을 표시한다.
- 영향 개수를 보여 준다.
- 자유 입력 대신 표준 사유 + 보충 메모를 사용한다.
- 고위험 작업은 재인증과 확인 문구를 요구한다.
- 실행 후 성공·부분 성공·실패 항목을 보고한다.

### 19.3 검색

운영자 검색은 업무 목적과 권한에 맞게 제한한다. 전화번호 전체, 실명, 결제 참조로 전역 검색하는 기능은 별도 승인과 감사를 요구한다.

### 19.4 내부 메모

- 사실, 판단, 다음 행동을 구분한다.
- 모욕적·차별적 표현을 금지한다.
- 관련 없는 개인정보를 기록하지 않는다.
- 사용자에게 공개 가능한 메모와 내부 제한 메모를 분리한다.

## 20. 운영 데이터와 지표

### 20.1 수요

- 일별 신규·재개 사건 수
- 유형·채널·언어·지역별 유입
- 시간대별 임박 예약 사건
- 자동 탐지 대 사용자 신고 비율

### 20.2 흐름

- 첫 응답 시간
- 해결 시간과 사용자 대기 포함 총 시간
- 큐 체류 시간
- 재배정 횟수
- 기한 초과율
- 재개율
- backlog 연령 분포

### 20.3 품질

- 이의 제기에서 뒤집힌 비율
- 품질 표본 불일치율
- 잘못된 병합·폐업·제재율
- 금전 조정 재작업률
- 개인정보 요청 누락 시스템 수
- 운영자 간 결정 일치율

### 20.4 안전과 공정성

- 광고 고객 여부별 콘텐츠 결정 차이
- 지역·언어별 처리 시간 차이
- 특정 점주가 반복 신고로 리뷰를 억압하는지
- 리뷰어 규모에 따른 제재 차이
- 운영자별 민감정보 조회와 이상 패턴

### 20.5 생산성 지표의 한계

시간당 처리 건수 하나로 운영자를 평가하면 어려운 사건 회피와 성급한 결정을 유도한다. 품질, 복잡도, 사용자 결과, 협업을 함께 본다.

## 21. 품질 보증

### 21.1 표본 검토

- 신규 운영자의 초기 결정 전수 검토
- 안정화 후 위험 기반 표본
- 정책이 바뀐 사유의 집중 표본
- 승인과 거절 양쪽 표본
- 광고 고객·비고객 비교 표본
- 자동화 결과 표본

### 21.2 캘리브레이션

같은 익명화 사건을 여러 검토자가 독립 판단한 뒤 차이를 토론한다. 합의율만 강제하지 않고 정책의 모호한 지점을 찾아 개정한다.

### 21.3 정책 변경 피드백

반복적으로 `other` 사유가 선택되거나 이의가 뒤집히는 영역은 운영자 교육 문제가 아니라 정책·도구 설계 문제일 수 있다.

### 21.4 운영자 안전

유해 콘텐츠를 다루는 운영자를 위해 경고, 흐림 처리, 노출 제한, 교대, 심리 지원을 고려한다. 원본 자동 재생을 금지한다.

## 22. 지식 관리

### 22.1 문서 종류

| 문서 | 역할 |
|---|---|
| Policy | 무엇이 허용되는가 |
| Procedure | 사건을 어떻게 처리하는가 |
| Runbook | 장애·실패를 어떻게 복구하는가 |
| Playbook | 반복 시나리오의 선택지와 판단 |
| Template | 사용자·점주 통지 |
| Decision log | 예외와 정책 해석의 기록 |

### 22.2 버전 관리

- owner, 승인자, 적용일, 다음 검토일
- 변경 요약과 영향받는 큐
- 교육 완료 여부
- 과거 사건에 소급 적용하는지
- 사용자 정책과 내부 절차의 연결

### 22.3 검색 가능한 사례

선례는 정책을 대신하지 않지만 일관성을 돕는다. 개인정보를 제거하고 결정 이유, 정책 버전, 뒤집힘 여부로 검색할 수 있게 한다.

## 25. 운영 준비도 체크리스트

### 제품 기능 공통

- [ ] 기능 owner와 운영 owner가 지정되었다.
- [ ] 실패 상태와 사용자 문구가 정의되었다.
- [ ] 고객지원이 상태를 안전하게 확인할 수 있다.
- [ ] 수동 복구 명령과 권한이 있다.
- [ ] 감사 로그가 남는다.
- [ ] 대량 오작동 kill switch가 있다.
- [ ] 지표, 경보, 대시보드가 있다.
- [ ] 운영 문서와 교육이 완료되었다.
- [ ] 개인정보 보존·삭제가 정의되었다.
- [ ] 사용자·점주 이의 제기 경로가 있다.

### 예약·결제

- [ ] 임박 예약 우선 큐가 있다.
- [ ] 결제 성공-예약 없음 탐지가 있다.
- [ ] 중복 예약 대응 훈련을 했다.
- [ ] 환불 재시도 전에 공급자 상태를 조회한다.
- [ ] 점주·사용자 변경 동의를 추적한다.
- [ ] 외부 채널 차단과 재조정이 가능하다.

### 콘텐츠·데이터

- [ ] 정책 버전과 결정 사유가 연결된다.
- [ ] 병합 영향 미리보기와 복구 계획이 있다.
- [ ] 영수증·위치 증빙 원본 접근이 제한된다.
- [ ] 점주 신고가 자동 삭제로 이어지지 않는다.
- [ ] 광고 관계가 운영 결정에 들어가지 않음을 감사할 수 있다.

## 26. 초기 운영 모델

### 제한 베타

- 서울의 제한된 지역과 협력 지점으로 데이터 범위를 좁힌다.
- 점주 claim과 지점 병합을 수작업 검수해 정책을 학습한다.
- 예약은 승인형, 결제 없음으로 시작한다.
- 리뷰 신고와 예약 사건을 한 티켓 시스템에 넣되 권한 뷰는 분리한다.
- 운영팀과 개발팀이 매일 실패 사례를 함께 본다.

### 공개 탐색 출시

- 음식점 데이터 수정 큐와 SLA
- 콘텐츠 신고·이의 제기
- 점주 인증과 공식 정보
- 개인정보 요청 채널
- 온콜과 상태 페이지

### 거래 출시

- 주말·야간 예약 지원
- 결제 조정과 환불 승인 체계
- 지점 긴급 연락 체계
- 공급자 장애 runbook
- 정기 재해 복구 훈련
