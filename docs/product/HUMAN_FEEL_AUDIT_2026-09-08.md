# 도락: 사람이 끝까지 다듬지 않은 듯한 부분과 개선안

작성일: 2026-09-08

## 결론

지금 도락의 문제는 색이나 폰트보다 **정보를 확신하는 방식과 기능 사이의 연결**이다. 실제 가격을 모르는 식당에 가격대가 붙고, 신고 기능을 만들었는데 안내는 메일 신고로 남아 있다. 리뷰보다 인증 설명이 앞서고, 운영 화면에는 개발 시연용 문장이 남아 있다.

이런 부분이 ‘각 화면을 따로 생성해서 붙인 서비스’처럼 느껴지게 한다. 해결 방향은 새 디자인이나 브랜드 선언 추가가 아니다. **모르는 정보는 모른다고 표시하고, 실제 식사 경험을 먼저 보여주며, 저장·신고의 다음 단계까지 연결하는 것**이다.

## 범위와 판단 기준

- 현재 저장소의 홈, 탐색, 식당 상세, 로그인, 저장, 리뷰 정책, 개인정보 안내, 운영 화면과 관련 데이터 변환 코드를 확인했다. 기준 커밋은 `7a2c0a9`이다.
- Hallmark의 근거 없는 주장, 과도한 설명·장식, 정보 위계, 입력·처리 상태 기준을 적용했다. 기능 연결 문제는 별도로 제품 흐름 문제라고 표시했다.
- ‘AI가 작성했다’는 저자 판별이 아니다. 코드로 확인되는 사실과 그로 인해 생길 수 있는 사용자 인상을 구분한 감사다.
- 이번 결과는 **소스 기반 감사**다. 운영 DB 전체, 실제 배포 화면의 픽셀·줄바꿈·대비, 사용자 행동은 검증하지 않았다. 아래 경로의 줄 번호는 감사 시점 기준이다.
- 이전 UI 감사에 있던 제거된 히어로, 이미지 자리 채우기, 폰트 미연결 문제를 현재 문제로 재사용하지 않았다.
- 최초 감사 작성 시점에는 제품 코드를 수정하지 않았다. 아래 구현 상태에서 후속 반영 내용을 기록한다.

## 구현 상태 — 2026-09-08

감사 후 아래 항목을 구현했다.

- **C1–C3 완료:** 가격 미수집 상태를 `null`로 분리하고 서울 공공데이터 수입분의 일괄 `₩₩`를 정리했다. 신고 정책과 개인정보 안내도 현재 기능에 맞췄다.
- **M1–M4 완료:** 공개 리뷰의 인증 배지를 짧은 이용 맥락과 접을 수 있는 ‘리뷰 정보’로 정리했다. 로그인 목적, 지역 제목, 평점 보조 문구도 실제 데이터에 맞췄다.
- **M5 완료:** 비로그인·체험 계정은 브라우저에 저장한 식당을 `/saved`에서 확인하고 삭제할 수 있다. 목록 개수는 같은 클라이언트 상태에서 갱신된다.
- **M6 완료:** 신고 검증·진행·성공·실패 안내를 운영자에게도 보이게 했고, ‘신고 검토 종료’와 ‘리뷰 공개 상태 변경’을 구분했다. 처리 이력 조회는 별도 기능으로 남아 있다.
- **M7, m1–m2 완료:** 운영 화면은 실제 업무와 건수를 먼저 보여주고, 빈 대기열의 과한 높이와 합성 데이터 고정 문구를 제거했다. 개인정보·영업시간의 개발용 표현도 정리했다.

DB 마이그레이션 `000014_nullable_branch_price.sql`을 적용했다. 타입 검사, 전체 테스트, 프로덕션 빌드를 통과했고 홈·상세·리뷰 원칙·저장·운영·개인정보 화면의 가로 넘침·클릭 문구 줄바꿈·대비를 확인했다. 320·375·414·768px 검증과 비로그인 저장 목록·개수·삭제 흐름도 통과했다. 운영 데이터에 대기 중인 후보가 없어 후보 승인 상호작용 검사는 실행하지 않았다.

## Critical — 사실과 기능이 어긋나는 부분

### C1. 근거 없는 가격대가 실제 정보처럼 보인다

**Tell:** Invented metric — 빈 정보를 그럴듯한 값으로 채움.

**근거:** [서울 식당 수입 스크립트](../../scripts/import-seoul-restaurants.mjs) 318–335행에서 모든 수입 행의 가격대 자리에 `2`를 넣는다. [카탈로그 변환](../../packages/server-catalog/src/postgres-catalog.ts) 131행은 이를 원화 기호로 바꾼다. [홈](../../apps/web/components/discovery.tsx) 663–665행은 평점이 없으면 이 가격대를 노출한다. 저장 목록에도 가격대가 표시된다.

**왜 어색한가:** 실제 수집한 가격과 내부 기본값을 구분하지 않는다. 사용자는 `₩₩`를 식당 선택의 근거로 읽는다. 신뢰성 높은 리뷰를 지향하면서 주변 정보부터 추정값이면 핵심 약속과 충돌한다.

**개선:** 가격 미수집 상태를 별도로 저장하고 가격 표시에서 제외한다. 실제 가격은 근거가 있을 때만 표시한다. 가격 필터도 미수집 항목을 중간 가격대로 취급하지 않는다.

**주의:** 기존 `price_band = 2` 전체를 일괄 지우면 실제 입력한 가격까지 손실될 수 있다. 출처와 입력 이력을 확인해 수입 기본값만 정리해야 한다. 운영 DB의 영향 건수는 별도 조회가 필요하다.

**완료 기준:** 가격을 수집하지 않은 식당이 홈·목록·상세·저장 어디에서도 `₩₩`로 표시되지 않는다.

### C2. 신고 기능과 리뷰 정책의 설명이 다르다

**Tell:** Honest-copy 위반 — 실제 기능과 안내의 불일치.

**근거:** [리뷰 정책](../../apps/web/app/review-policy/page.tsx) 94–98행은 문의 주소가 설정되면 리뷰 하단에서 메일로 신고한다고 설명한다. 실제 [신고 폼](../../apps/web/components/review-report-form.tsx)은 앱 내부 API에 신고를 제출한다.

**왜 어색한가:** 기능을 추가한 뒤 서비스 전체의 문장을 다시 읽지 않은 흔적이다. 특히 신고 방식이 어긋나면 운영 원칙 전체를 믿기 어렵다.

**개선 문구:** “리뷰 아래 ‘문제 신고’에서 사유를 보내주세요. 신고 내용은 공개되지 않습니다.”

**완료 기준:** 리뷰 정책과 신고 폼의 제출 방법·공개 범위가 일치한다. 아직 없는 회신 기능이나 처리 기한을 약속하지 않는다.

### C3. 개인정보 안내에 개발 메모와 빠진 수집 항목이 남아 있다

**Tell:** Placeholder copy / Honest-copy 위반.

**근거:** [개인정보 안내](../../apps/web/app/privacy/page.tsx) 22행의 “도락 MVP 기준”, 60행의 “정식 공개 전에는 … 이메일로 … 반드시 교체합니다.”가 공개 본문에 있다. 28–39행 수집 목록에는 저장한 식당, 신고 내용과 계정 연결, 이용 방식·이해관계 자기신고가 구체적으로 반영되지 않았다. 연락처는 환경변수 유무에 따라 표시되므로 실제 운영 연락처가 없다고 단정하지는 않는다.

**왜 어색한가:** 이용자에게 설명하는 문서 안에 개발자에게 지시하는 문장이 들어 있다. 새 기능마다 데이터는 늘었지만 안내는 갱신되지 않았다.

**개선:** 내부 작업 지시를 제거하고 실제 저장 필드와 공개 여부를 대조해 목록을 다시 쓴다. 공개 연락처가 실제로 동작하는지도 확인한다. 배달·포장을 포함하도록 ‘방문일’ 대신 실제 데이터 의미에 맞는 ‘이용일’을 사용한다.

**완료 기준:** 각 수집 항목을 구현에 대응시킬 수 있고 공개 문서에 배포 준비 메모가 없다. 이는 문서·구현 정합성 지적이며 법률 적합성 판단은 아니다.

## Major — 화면은 있지만 이용 흐름을 끝까지 다듬지 않은 부분

### M1. 리뷰보다 ‘신뢰 장치 설명’이 먼저 보인다

**Tell:** Over-explanation / 위계 평탄화.

**근거:** [식당 상세](../../apps/web/app/restaurants/[publicId]/page.tsx) 221–262행에서 이용 방식, 이메일 확인, 이용일 자기입력 또는 증빙 상태, 이해관계 확인을 연속 라벨로 표시하고 ‘이용 증빙 미확인’도 덧붙인다. 이메일 확인에는 방패 아이콘이 사용된다.

**왜 어색한가:** 독자가 알고 싶은 음식 경험보다 시스템이 자신의 검증 구조를 설명하는 데 힘을 쓴다. 이메일 확인이 식사 경험의 인증처럼 읽힐 위험도 있다.

**개선:** 작성자·평점·이용일·이용 방식을 짧은 메타정보로, 실제 리뷰 본문을 중심으로 배치한다. 이해관계는 “협찬 없음 · 작성자 응답”처럼 출처를 분명히 한다. 이메일 확인과 증빙 상태의 자세한 설명은 ‘리뷰 정보’에서 제공한다. 중요한 미확인 사실을 숨기거나 자기신고를 인증으로 승격하면 안 된다.

**완료 기준:** 본문을 읽기 전에 여러 인증 배지를 해석하지 않아도 된다. 계정 확인과 식사 증빙이 명확히 구분된다.

### M2. 로그인 화면이 저장하러 온 사람에게 리뷰 이야기를 한다

**Tell:** Generic copy — 진입 목적과 맞지 않는 설명.

**근거:** [로그인](../../apps/web/app/signin/page.tsx) 34행 제목은 “리뷰를 쓰기 전에 계정을 확인합니다.”다. 하지만 [저장 페이지](../../apps/web/app/saved/page.tsx) 14행도 이 화면으로 보낸다. 로그인 57–59행에는 방문 여부를 별도 확인하고 영수증·예약 내역으로 확인 표시를 한다는 설명도 있다. 현재 증빙 제출 흐름은 없어 현행 기능으로 오해할 수 있다.

**개선 문구:** 제목은 “로그인”, 설명은 “식당을 저장하고 리뷰를 남겨보세요.” 정도로 줄인다. 저장 진입이면 “저장한 식당을 보려면 로그인해 주세요.”처럼 목적에 맞춰 쓴다. 증빙 수집이 없는 상태에서는 “로그인은 식사 여부를 인증하지 않습니다.”까지만 정확히 안내한다.

**완료 기준:** 저장·리뷰 양쪽에서 로그인 후 원래 목적지로 돌아간다. 현재 제공하지 않는 증빙 절차를 있는 것처럼 안내하지 않는다.

### M3. ‘인기 지역’의 근거가 인기가 아니다

**Tell:** Unsupported claim — 데이터와 제목의 의미 불일치.

**근거:** [홈](../../apps/web/components/discovery.tsx) 325–334행에서 지역을 등록 식당 수로 정렬하고 598행에서 “인기 지역”이라고 부른다. 조회·저장·리뷰 활동 기준이 아니다.

**개선:** 현재 로직을 유지한다면 “식당이 많은 지역”으로 바꾼다. 지역을 탐색하는 영역으로 재구성하면 “지역별 식당”도 가능하다. ‘인기’는 실제 측정 지표와 기간이 생긴 뒤 사용한다.

**완료 기준:** 제목을 설명할 때 데이터에 없는 의미를 보태지 않아도 된다.

### M4. 낮은 평점까지 ‘보통’으로 포장한다

**Tell:** Generic evaluative copy — 자동 평가 문구가 실제 값을 왜곡함.

**근거:** [탐색](../../apps/web/components/discovery.tsx) 65–69행과 [저장 목록](../../apps/web/components/saved-list.tsx) 8–12행의 평가 함수는 리뷰가 5건 이상이면 4.5 이상 ‘아주 좋음’, 4 이상 ‘좋음’, 나머지 전부 ‘보통’으로 분류한다. 1점도 ‘보통’에 포함된다.

**개선:** 자동 칭찬·판정 문구를 없애고 평점과 “리뷰 N건”을 보여준다. 표본이 적으면 “리뷰가 적어요”로 분리한다. 평가 등급을 유지하려면 낮은 점수까지 포함한 기준과 근거가 먼저 필요하다.

**완료 기준:** 1점·3점·4점·평점 없음·리뷰 4건과 5건 경계에서 숫자와 말이 충돌하지 않는다.

### M5. 비로그인 저장과 저장 목록의 연결이 끊긴다

**Tell:** 제품 흐름 문제 — 동작은 구현했지만 돌아오는 길이 부족함.

**근거:** [탐색](../../apps/web/components/discovery.tsx) 156–164행과 524–528행은 비로그인 저장을 브라우저에 보관한다. 반면 [헤더](../../apps/web/components/site-header.tsx) 19–26행은 로그인 상태에만 저장 링크를 보여주고, 저장 페이지는 비로그인 접근을 로그인으로 보낸다. 저장 페이지 30행의 개수는 서버 초기값이고, 목록 삭제는 `SavedList` 내부 상태라 숫자가 함께 갱신되지 않는다.

**왜 어색한가:** 저장 버튼을 눌렀을 때와 다시 찾아볼 때의 제품 규칙이 다르다. 항목을 지웠는데 상단 개수가 그대로인 것도 부분별 구현의 흔적이다.

**개선:** 저장 진입점은 항상 제공한다. 기존 브라우저 저장을 활용해 비로그인 목록도 보여주고 계정 동기화가 필요한 순간에 로그인 이유를 설명하는 방향을 권장한다. 목록과 개수는 같은 상태에서 계산한다. 로그인 시 병합 로직은 보존한다.

**완료 기준:** 비로그인 저장 → 재방문 → 목록 확인 → 로그인 병합 → 삭제까지 이어진다. 마지막 항목 삭제 및 실패 복구 시 개수와 빈 상태가 일치한다.

### M6. 신고 처리 결과가 눈에 보이지 않는다

**Tell:** Input-state / 제품 흐름 문제.

**근거:** [신고 대기열](../../apps/web/components/report-queue.tsx) 35–68행에서 검증 오류·실패·성공 안내를 `message`에 넣지만 90행 출력은 `sr-only`다. 일반 화면에서는 메시지가 안 보인다. 성공 메시지에만 ‘공개 숨김은 리뷰 관리에서 별도 진행’이라는 중요한 구분도 들어 있다.

**왜 어색한가:** 운영자는 사유를 짧게 썼을 때 왜 동작하지 않는지, ‘처리 완료’가 리뷰 숨김까지 뜻하는지 화면만 보고 판단하기 어렵다. 지난번 추가한 신고 기능도 이 문제에서 예외가 아니다.

**개선:** 오류·진행·결과 메시지를 해당 작업 근처에 시각적으로도 표시하고 라이브 안내는 유지한다. 신고 검토 종료와 리뷰 공개 숨김을 버튼·설명에서 구분한다. 처리 이력을 다시 열어볼 경로도 후속으로 제공한다.

**완료 기준:** 짧은 사유, 요청 중, 서버 오류, 검토 종료, 기각을 눈과 스크린리더 모두로 구분할 수 있다. 신고 종료를 리뷰 삭제·숨김으로 오해하지 않는다.

### M7. 운영 화면이 업무 도구보다 제품 시연 설명처럼 보인다

**Tell:** Inflated explanatory copy / 업무 위계 불일치.

**근거:** [운영 화면](../../apps/web/app/ops/page.tsx) 80–86행은 “수집 후보 → 검수 결정”, “원문을 보존하고, 지점으로 만들기 전에 사람이 확인합니다.”와 API·저장 구조 설명을 앞세운다. 101행의 “합성 데이터 환경” 표기는 실제 데이터 모드와 별개로 고정 문자열이다. 후보 검수·신고·리뷰 관리가 함께 있는데 제목은 후보 검수 중심이다.

**개선:** 제목을 “운영”으로 정리하고 처리할 업무와 건수를 먼저 보여준다. 신고·리뷰·후보 영역을 명확히 나눈다. 빈 업무 영역은 짧게 접고, 개발 구조 설명은 개발 문서로 옮긴다. 환경 표시는 실제 모드에 맞을 때만 사용한다.

**완료 기준:** 운영자가 첫 화면에서 처리할 업무로 바로 이동한다. 운영 데이터에 합성 데이터라는 고정 안내가 붙지 않는다.

## Minor — 내용은 유지하고 말투·표시를 정리할 부분

### m1. 개인정보 안내가 실용 문서보다 편집 디자인 견본처럼 시작한다

**Tell:** Decorative-without-purpose / inflated editorial copy.

**근거:** [개인정보 안내](../../apps/web/app/privacy/page.tsx) 19행의 “도락 운영 원칙 02”와 “필요한 정보만, 쓰임이 보이게 다룹니다.”라는 제목.

**개선:** 장식 번호를 없애고 제목을 “개인정보 처리 안내”로 쓴다. 수집 정보·이용 목적·보관·문의 순서로 바로 읽게 한다. C3의 사실 정정과 함께 처리하면 된다.

### m2. 식당마다 ‘확인 전’이라는 내부 작업 상태를 보여준다

**Tell:** Generic placeholder copy.

**근거:** [식당 상세](../../apps/web/app/restaurants/[publicId]/page.tsx) 112행의 “영업 정보 확인 전”은 영업시간 데이터와 무관한 고정 표시다.

**개선:** 영업시간이 없으면 정보 영역에서 “영업시간 정보 없음”을 한 번만 표시한다. 시간이 있어도 실시간 영업 여부를 검증하지 않았다면 ‘영업 중’이라고 단정하지 않는다. 전화·지도 등 실제 제공 가능한 확인 수단을 연결한다.
