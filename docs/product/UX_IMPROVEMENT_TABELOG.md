## 0. 전제

타베로그에서 가져올 것은 **정보 구조·밀도·탐색 동선**이다. 표·배지·문구 외형은 가져오지 않는다 (DESIGN_SYSTEM §2 "일본 서비스의 표, 배지, 문구를 그대로 모방한 화면" 금지).

| 가져온다 | 가져오지 않는다 |
|---|---|
| 지역 × 장르 2축 탐색, 모든 항목에 건수 표시 | 예약 날짜·시간·인원 검색 (도락에 예약 없음) |
| 목록 = 필터 사이드바 + 순위 카드 + 번호 페이지네이션 | 다국어 셀렉터, 앱 QR |
| 카드 한 장에 판단 근거 전부 (평점·리뷰수·가격·위치·영업정보) | 어워드/백명점 배지 남발 (EDITORIAL_AWARDS 단계까지 보류) |
| 상세 = 헤더 요약 + 탭 + 기본정보 표 + 지도 + 유사 식당 | 사진 그리드 중심 레이아웃 (사진 데이터 없음, 사진보다 근거 우선) |
| 평점 숫자에 등급 색상 부여 | 3.5 오렌지 등 타베로그 컬러 체계 |

## 2. 개선안 (우선순위)

### P0 — 지금 깨진 것과 탐색 골격

#### 2.1 목록 라우트 신설 `/r/[district]/[cuisine]`
- 문제: `/search` 404. 목록이 홈에 묶여 URL 공유·복귀 불가.
- 적용: `app/r/[[...path]]/page.tsx` 하나. 경로 = `서울/{구}/{장르}` 선택형, 나머지 조건은 쿼리 (`?q=&price=&sort=&page=`). 홈의 `#directory` 블록을 이 페이지로 이동하고 `discovery.tsx` 에서 `mode="results"` 소비.
- 예: `/r/마포구`, `/r/마포구/japanese?price=2&sort=rating&page=3`
- 파일: `app/api/v1/branches/route.ts` 에 `district`, `neighborhood`, `cuisine`, `price`, `sort`, `page` 파라미터 추가. 지역을 `q` 에 섞는 현행 방식 제거.

#### 2.2 헤더 상시 검색창
- 모든 페이지 헤더 중앙에 `BranchSearchForm` 축소형. 60rem 미만은 아이콘 → 펼침.
- 파일: `components/site-header.tsx`. 레이아웃이 페이지별 렌더인 점은 유지 (변경 범위 최소).

#### 2.3 서버 정렬 + 건수 + 번호 페이지네이션
- 정렬: `sort=default|rating|reviews` 를 SQL ORDER BY 로. 기본순 정의는 SEARCH_SYSTEM 따름 (없으면 `review_count desc, rating desc`).
- 건수: 목록 상단 `1–20 / 1,284곳`. `SELECT count(*) OVER()` 한 번.
- 페이지: 20건 고정, `<nav>` 번호 + 이전/다음. 무한스크롤 코드 삭제. `rel=prev/next` 메타.

#### 2.4 카드 재설계 (판단 근거 한 장)
```
┌──────────────────────────────────────────────────┐
│ 12  성산동 · 일식 · 라멘                           │
│     식당 이름                          4.3 ●좋음   │
│     한줄설명 (1줄 말줄임)              리뷰 128     │
│     ₩₩ · 마포구 성산동 · 홍대입구역 도보 9분        │
│     오늘 11:30–21:30 · 월 휴무          [저장 ♡ 41] │
│     대표메뉴 태그 최대 3개                          │
└──────────────────────────────────────────────────┘
```
- 순위 번호: 정렬 기준 내 순번 (offset + index).
- 평점 등급 라벨: RATING_SYSTEM 의 구간에 맞춰 `아직 적음(리뷰<5) / 보통 / 좋음 / 아주 좋음`. 색은 `tokens.css` 의 forest/brass/clay 재사용, 새 색 추가 없음.
- 사진 placeholder 제거. 사진이 생기면 오른쪽 썸네일 1장 슬롯만 (MEDIA_PIPELINE 이후).
- 거리: 좌표 있으므로 PostGIS 로 최근접 지하철역 계산 가능. 역 데이터 없으면 이 줄은 `동` 까지만.
- 영업: `opening_hours` 문자열 파싱은 하지 않음. 원문 그대로 1줄 + `closed_days`. "영업 중" 판정은 구조화 데이터 들어온 뒤.

#### 2.5 필터 사이드바 정리
- 지역: `구 > 동` 아코디언 유지, 건수 표시 유지. 선택은 URL 경로 변경.
- 장르: 6종 → 다중 선택 아님, 단일 유지 (현행 데이터가 단일 `cuisine_key`).
- 가격대: `₩ ~ ₩₩₩₩` 체크박스 (컬럼 이미 존재). 실데이터에 값 없으면 "확인 전" 항목으로 묶어 노출.
- 평점: `4.0 이상 / 3.5 이상` 두 개만.
- 모바일: 기존 `<details>` 접이식 유지, 적용 조건 수를 요약 칩으로 상단 노출.

### P1 — 홈과 상세를 "포털 + 레퍼런스"로

#### 2.6 홈 = 인덱스 페이지
섹션 순서:
1. 검색 (히어로 축소, 문장 1줄)
2. 인기 지역 8개: 구 이름 + 건수 (썸네일은 사진 데이터 전까지 생략, 지도 크롭 이미지도 비용이라 보류)
3. 인기 장르 6개: 장르 + 건수
4. 최근 리뷰 6건: 식당명·평점·본문 2줄 (community.reviews 최신순, 홈에서 신뢰 서사 대체)
5. 전체 지역 인덱스: 25개 구 → 동 링크 텍스트 목록 (색인 진입점)
6. trust-strip 은 푸터 위 1줄로 축소

홈에서 60건 목록 제거. 목록은 2.1 라우트로.

#### 2.7 상세 페이지 재배열
```
브레드크럼  서울 › 마포구 › 성산동 › 일식
[식당 이름]                              4.3 ●좋음  리뷰 128  저장 41
일식 · 라멘 · 성산동 · 홍대입구역 도보 9분 · ₩₩
[전화]  [카카오맵에서 보기]  [저장]
─ 탭(앵커): 개요 | 메뉴 | 리뷰 128 | 지도 · 주변
개요: 한줄설명, 영업시간/휴무, 대표메뉴 3개 요약, 출처·검증일
메뉴: 대표메뉴 전체 (가격 "확인 전" 표기 유지)
리뷰: 요약(분포 막대 1~5) → 목록 → 작성 폼
지도·주변: 카카오맵 + 같은 동 상위 5곳 + 같은 장르 상위 5곳
기본정보 표: 식당명/장르/주소/전화/홈페이지/영업시간/휴무일/가격대/좌석·주차·결제(컬럼 추가 시)/출처/검증일
```
- 지도는 상단 요약에서 빼고 탭 마지막으로. 첫 화면은 이름·평점·영업 정보에 집중.
- 유사 식당: 별도 추천 시스템 없이 SQL 2개 (`same neighborhood`, `same cuisine`, `rating desc limit 5`). RECOMMENDATION_SYSTEM 전까지의 최소 구현.
- 리뷰 분포 막대: `count group by rating` 1쿼리.

#### 2.8 저장 서버화 + 저장 목록
- `community.saved_branches(user_id, branch_id)` 테이블. 로그인 시 localStorage 값 1회 병합.
- `/saved` 페이지 = 2.1 목록 컴포넌트 재사용.
- 카드·상세에 저장 수 노출 (타베로그 "保存" 카운트 상당).

## 3. 하지 않을 것

- 예약 조건(날짜·시간·인원) 검색 UI — 예약 기능 없음
- 무한스크롤과 번호 페이지 병행 — 하나만 (번호)
- Tailwind/shadcn 도입 — `globals.css` + `tokens.css` 로 충분, 마이그레이션 비용만 생김
- 다크모드 — 요청 없음
- 헤더/푸터 공유 레이아웃으로 재구성 — 동작에 영향 없음, 페이지별 렌더 유지

## 4. 실행 순서

1. `/r/[[...path]]` 라우트 + API 파라미터 (2.1) → `/search` 404 해소. 홈 목록은 일단 유지.
2. 서버 정렬·건수·페이지네이션 (2.3), 무한스크롤 삭제.
3. 카드 재설계 (2.4), 필터 정리 (2.5).
4. 헤더 검색창 (2.2).
5. 홈에서 목록 제거하고 인덱스화 (2.6).
6. 상세 재배열 + 유사 식당 + 리뷰 분포 (2.7).
7. 저장 서버화 (2.8).

1~4는 `discovery.tsx` 하나가 대부분이라 한 브랜치에서 처리 가능. 5 이후는 각각 독립 PR.
