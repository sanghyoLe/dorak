# 도락 제품 요구사항 명세

| 항목 | 내용 |
| --- | --- |
| 문서 상태 | Draft |
| 문서 버전 | 0.1.0 |
| 제품명 | 도락(DORAK) |
| 제품 정의 | 신뢰할 수 있는 음식점 데이터, 리뷰, 평점, 랭킹, 예약을 제공하는 전국 단위 외식 플랫폼 |
| 주요 독자 | 제품, 디자인, 개발, 데이터, 운영, 영업, 법무 |

## 1. 문서 목적

이 문서는 도락의 전체 제품 범위와 사용자별 기능 요구사항을 정의한다. 데이터 구조, 평점 계산, API, 운영 정책은 별도 문서에서 구체화하며, 모든 후속 설계는 이 문서의 요구사항 ID를 참조한다.

도락은 특정 음식 장르나 특정 지역만을 위한 서비스가 아니다. 전국 음식점을 대상으로 다음 세 제품을 하나의 플랫폼으로 제공한다.

1. 소비자가 좋은 식당을 탐색하고 평가하고 예약하는 서비스
2. 음식점 데이터와 리뷰 신뢰도를 관리하는 평가 플랫폼
3. 점주가 매장 정보와 예약, 고객 접점을 관리하는 업무 도구

## 2. 제품 비전

> 좋은 식당을 찾는 즐거움을, 신뢰할 수 있는 정보로 만든다.

도락이 해결하려는 문제는 음식점 정보의 부족이 아니라 신뢰의 부족이다. 사용자는 광고성 콘텐츠, 조작 리뷰, 기준 없는 별점, 오래된 영업 정보 사이에서 실제로 만족할 식당을 찾기 어렵다. 점주는 여러 플랫폼에 흩어진 정보를 반복해서 관리하고, 허위 리뷰와 불투명한 노출 정책에 대응하기 어렵다.

도락은 음식점의 인기도와 평가 품질을 구분하고, 광고와 평점을 분리하며, 리뷰어의 취향과 전문성을 설명 가능한 방식으로 보여준다.

## 3. 제품 원칙

### P-01. 평점과 광고의 독립

유료 상품 구매 여부는 음식점 평점에 영향을 주지 않는다. 광고 노출은 광고임을 명시하고, 평점순 및 랭킹과 시각적으로 구분한다.

### P-02. 단순 평균보다 신뢰도

공개 점수는 리뷰 수, 리뷰어별 평가 기준, 장르 전문성, 방문 인증, 최신성, 조작 위험을 고려한다.

### P-03. 데이터 출처와 변경 이력

음식점 정보의 출처, 마지막 확인 시각, 변경 이력을 내부적으로 추적한다. 사용자에게 중요한 정보에는 최신 확인 날짜를 표시한다.

### P-04. 점주의 편집권과 사용자의 평가권 분리

점주는 영업정보와 공식 콘텐츠를 관리할 수 있지만 사용자 리뷰와 평점을 임의로 삭제하거나 수정할 수 없다. 신고와 이의 제기는 별도 운영 절차를 따른다.

### P-05. 취향 차이의 설명

좋고 나쁨만 표시하지 않고 리뷰어의 취향, 주문 메뉴, 방문 맥락, 가격대, 재방문 의사를 함께 제공한다.

### P-06. 공개 정보와 개인 정보의 최소 결합

리뷰 신뢰도를 높이는 데 필요한 인증은 수행하되, 영수증 원본, 결제 정보, 위치 이력 등 민감한 원본 데이터의 보관을 최소화한다.

### P-07. 전국 범위, 지역별 품질 관리

전국 음식점 원장을 운영하되 검색 결과와 랭킹은 지역 및 장르별 데이터 충분성을 반영한다. 데이터가 부족한 영역을 높은 확신의 랭킹처럼 표현하지 않는다.

## 4. 목표와 비목표

### 4.1 제품 목표

- 사용자가 광고 여부와 무관한 음식점 평가를 확인할 수 있다.
- 지역, 장르, 가격, 상황에 맞는 음식점을 빠르게 찾을 수 있다.
- 리뷰를 작성한 사람의 전문성과 취향을 이해할 수 있다.
- 음식점의 이전, 폐업, 휴무, 메뉴 변경을 신속하게 반영한다.
- 점주가 한 곳에서 공식 정보와 예약 접점을 관리할 수 있다.
- 운영자가 리뷰와 데이터 분쟁을 근거와 이력에 따라 처리할 수 있다.
- 한국 방문 외국인이 국내 음식점을 탐색하고 예약할 수 있다.

### 4.2 초기 비목표

다음 기능은 장기적으로 연계할 수 있지만 핵심 플랫폼이 안정되기 전까지 직접 운영하지 않는다.

- 배달 물류망
- 식자재 구매 및 공급망
- 자체 간편결제 네트워크
- 식당용 POS 전체 대체
- 음식점 프랜차이즈 운영 대행
- 사용자 간 중고거래 또는 일반 지역 커뮤니티

## 5. 사용자 유형

### 5.1 비회원 탐색자

검색 엔진, 공유 링크, 지도 탐색을 통해 음식점 정보를 확인한다. 가입 없이 검색, 상세 페이지, 공개 리뷰, 랭킹을 볼 수 있어야 한다.

### 5.2 일반 회원

음식점을 저장하고, 리뷰를 작성하고, 다른 리뷰어를 팔로우하며, 예약을 관리한다.

### 5.3 전문 리뷰어

특정 지역 또는 음식 장르에 높은 경험과 신뢰도를 가진 회원이다. 일반 회원과 별도 가입 유형이 아니라 활동과 검증 결과로 전문성이 형성된다.

### 5.4 점주 및 매장 관리자

사업자 또는 위임 관계를 인증하고 음식점의 공식 정보, 메뉴, 사진, 예약 재고를 관리한다.

### 5.5 음식점 그룹 관리자

프랜차이즈 본사, 호텔, 외식 기업처럼 여러 브랜드와 지점을 관리한다. 본사 권한과 지점 권한을 분리한다.

### 5.6 데이터 운영자

신규 음식점, 중복, 이전, 폐업, 카테고리, 주소, 메뉴 제보를 검수한다.

### 5.7 콘텐츠 모더레이터

리뷰, 사진, 댓글, 프로필, 신고를 정책에 따라 검토하고 조치한다.

### 5.8 고객 지원 및 분쟁 담당자

예약, 결제, 노쇼, 리뷰 이의 제기, 개인정보 요청을 처리한다.

### 5.9 시스템 관리자 및 감사자

역할과 권한을 관리하고 민감한 운영 행위를 감사한다. 일반 운영자에게 불필요한 개인정보 접근 권한을 부여하지 않는다.

## 6. 핵심 사용자 여정

### J-01. 주변 음식점 발견

1. 사용자가 현재 위치 또는 동네를 선택한다.
2. 지도나 목록에서 음식점을 탐색한다.
3. 장르, 가격, 영업 여부, 이용 목적을 필터링한다.
4. 음식점 상세 페이지에서 평점 근거와 리뷰를 확인한다.
5. 길 찾기, 저장, 전화 또는 예약을 선택한다.

### J-02. 목적형 검색

1. 사용자가 음식, 상호, 지역, 메뉴 또는 자연어 조건을 검색한다.
2. 시스템이 음식점, 메뉴, 지역, 리스트, 리뷰어 결과를 구분해 제공한다.
3. 사용자가 정렬과 필터를 적용한다.
4. 결과가 부족하면 조건 완화 또는 인접 지역을 제안한다.

### J-03. 방문 기록과 리뷰 작성

1. 사용자가 방문한 음식점을 선택한다.
2. 방문일, 동행 유형, 주문 메뉴, 지출액을 입력한다.
3. 평점, 재방문 의사, 리뷰, 사진을 작성한다.
4. 영수증, 예약, QR, 위치 등의 방법으로 방문을 인증한다.
5. 시스템이 정책 위반 및 조작 위험을 검사한다.
6. 게시 후 음식점 점수는 다음 계산 주기에 반영된다.

### J-04. 신뢰할 리뷰어 발견

1. 사용자가 음식점 리뷰에서 리뷰어 프로필을 연다.
2. 리뷰어의 주요 활동 지역, 전문 장르, 평가 분포, 공개 리스트를 확인한다.
3. 취향이 맞는 리뷰어를 팔로우한다.
4. 홈 피드와 검색에서 팔로우한 리뷰어의 평가를 우선 참고한다.

### J-05. 점주 매장 등록

1. 점주가 기존 음식점을 검색하거나 신규 음식점을 제보한다.
2. 사업자등록 정보, 인허가 정보 또는 위임 서류로 권한을 인증한다.
3. 운영자가 자동 및 수동 검증을 수행한다.
4. 승인 후 점주가 공식 정보와 예약 설정을 관리한다.

### J-06. 음식점 정보 수정

1. 사용자 또는 점주가 정보 오류를 제보한다.
2. 제보 대상 필드와 근거를 제출한다.
3. 자동 검증 또는 운영자 검수를 거친다.
4. 승인된 변경은 출처와 변경 이력을 남기고 반영한다.
5. 영향받은 사용자와 점주에게 필요한 경우 알림을 보낸다.

### J-07. 예약

1. 사용자가 날짜, 시간, 인원, 좌석 또는 코스를 선택한다.
2. 시스템이 실시간 재고와 예약 정책을 표시한다.
3. 사용자가 연락처와 결제 또는 예약금 정보를 확인한다.
4. 예약이 확정되고 사용자와 점주에게 알림이 전송된다.
5. 변경, 취소, 노쇼, 환불 상태가 일관되게 관리된다.

### J-08. 리뷰 신고와 이의 제기

1. 사용자 또는 점주가 위반 사유를 선택하고 신고한다.
2. 시스템이 동일 신고, 긴급성, 노출 위험을 분류한다.
3. 운영자가 리뷰와 비공개 증빙을 검토한다.
4. 유지, 제한, 블라인드, 삭제, 계정 조치 중 하나를 결정한다.
5. 당사자에게 결과와 이의 제기 방법을 안내한다.

## 7. 정보 구조

### 7.1 소비자 앱 하단 내비게이션

1. 홈
2. 검색
3. 지도
4. 저장
5. 내 활동

### 7.2 웹 정보 구조

- `/`: 홈 및 지역 진입
- `/search`: 통합 검색
- `/map`: 지도 탐색
- `/restaurants/{restaurantSlug}-{branchId}`: 음식점 상세
- `/regions/{regionSlug}`: 지역 페이지
- `/categories/{categorySlug}`: 장르 페이지
- `/rankings/{region}/{category}`: 랭킹
- `/reviewers/{handle}`: 리뷰어 프로필
- `/lists/{listSlug}-{listId}`: 공개 리스트
- `/awards/{year}`: 연간 어워드
- `/reservations`: 예약 내역
- `/me`: 개인 활동
- `/owner`: 점주 서비스 진입

### 7.3 점주 콘솔

- 대시보드
- 매장 정보
- 메뉴
- 사진 및 콘텐츠
- 공지와 영업 상태
- 리뷰 및 답변
- 예약과 좌석
- 고객 통계
- 광고 및 프로모션
- 구성원과 권한
- 정산 및 계약

### 7.4 운영자 콘솔

- 데이터 검수 큐
- 중복 및 병합 후보
- 리뷰 신고 큐
- 사용자 위험 신호
- 점주 인증
- 예약 분쟁
- 개인정보 요청
- 점수 계산 상태
- 운영 정책과 사유 코드
- 감사 로그

## 8. 소비자 기능 요구사항

### 8.1 계정과 인증

- **ACC-001** 비회원은 공개 음식점 정보와 공개 리뷰를 조회할 수 있어야 한다.
- **ACC-002** 사용자는 Apple, Google, Kakao 및 이메일 기반 방식 중 지원되는 수단으로 가입할 수 있어야 한다.
- **ACC-003** 리뷰 작성, 예약, 점주 기능에는 위험 수준에 맞는 추가 인증을 요구할 수 있어야 한다.
- **ACC-004** 사용자는 연결된 로그인 수단을 추가하거나 안전하게 해제할 수 있어야 한다.
- **ACC-005** 사용자는 프로필 공개 범위와 팔로우 허용 범위를 설정할 수 있어야 한다.
- **ACC-006** 사용자는 계정 및 개인 데이터 삭제를 요청할 수 있어야 한다.
- **ACC-007** 시스템은 제재 계정의 재가입과 다중 계정 악용 신호를 탐지할 수 있어야 한다.

### 8.2 검색

- **SRC-001** 사용자는 음식점명, 지점명, 메뉴명, 음식 장르, 지역명으로 검색할 수 있어야 한다.
- **SRC-002** 검색은 한글 초성, 띄어쓰기, 일반적인 오탈자, 과거 상호를 처리해야 한다.
- **SRC-003** 동일 상호의 여러 지점은 개별 지점으로 구분해야 한다.
- **SRC-004** 검색 결과는 음식점, 메뉴, 지역, 리스트, 리뷰어를 유형별로 구분해야 한다.
- **SRC-005** 사용자는 거리, 평점, 리뷰 수, 인기, 신규 등록, 예약 가능 여부로 정렬할 수 있어야 한다.
- **SRC-006** 광고 정렬과 자연 검색 정렬을 명시적으로 구분해야 한다.
- **SRC-007** 폐업 음식점은 기본 결과에서 제외하되 직접 검색 시 상태와 함께 확인할 수 있어야 한다.
- **SRC-008** 검색 결과가 부족할 경우 철자 교정, 인접 지역, 상위 장르를 제안해야 한다.
- **SRC-009** 검색 로그는 개인정보 보호 정책에 따라 분석 가능하게 저장해야 한다.

### 8.3 지도 탐색

- **MAP-001** 사용자는 현재 지도 영역 안의 음식점을 조회할 수 있어야 한다.
- **MAP-002** 지도 이동 후 이 지역 다시 검색을 실행할 수 있어야 한다.
- **MAP-003** 확대 수준에 따라 마커를 군집화해야 한다.
- **MAP-004** 선택한 필터와 정렬은 목록과 지도에 동일하게 적용되어야 한다.
- **MAP-005** 위치 권한을 거부한 사용자도 지역 검색으로 모든 핵심 기능을 사용할 수 있어야 한다.
- **MAP-006** 사용자의 지속적인 위치 이력을 기본값으로 저장하지 않아야 한다.
- **MAP-007** 경계 지역과 다층 건물 내 지점의 위치를 운영자가 교정할 수 있어야 한다.

### 8.4 음식점 상세

- **RST-001** 음식점명, 지점명, 주소, 전화번호, 장르, 가격대, 영업 상태를 표시해야 한다.
- **RST-002** 오늘의 영업시간, 브레이크타임, 라스트오더, 임시 휴무를 표시해야 한다.
- **RST-003** 영업정보의 마지막 확인일과 공식 정보 여부를 표시해야 한다.
- **RST-004** 공개 점수, 리뷰 수, 방문 인증 리뷰 비율, 점수 업데이트일을 표시해야 한다.
- **RST-005** 메뉴별 이름, 설명, 가격, 사진, 판매 상태를 표시할 수 있어야 한다.
- **RST-006** 사용자 사진과 점주 공식 사진을 구분해야 한다.
- **RST-007** 편의시설, 좌석, 주차, 접근성, 아동 동반, 반려동물, 포장 정보를 표시할 수 있어야 한다.
- **RST-008** 폐업, 이전, 임시 휴업 상태를 눈에 띄게 표시해야 한다.
- **RST-009** 이전한 음식점은 가능한 경우 새 지점 페이지로 연결해야 한다.
- **RST-010** 사용자는 잘못된 정보를 필드 단위로 제보할 수 있어야 한다.
- **RST-011** 음식점 관계자의 공식 공지와 사용자 생성 콘텐츠를 구분해야 한다.
- **RST-012** 길 찾기는 선택한 지도 사업자 또는 기기 기본 지도 앱으로 연결할 수 있어야 한다.

### 8.5 리뷰

- **REV-001** 리뷰는 특정 음식점 지점과 방문 경험에 연결되어야 한다.
- **REV-002** 사용자는 방문일, 방문 시간대, 동행 유형, 주문 메뉴를 입력할 수 있어야 한다.
- **REV-003** 사용자는 종합 평가와 재방문 의사를 입력할 수 있어야 한다.
- **REV-004** 장르별 세부 평가는 제품 정책에 따라 동적으로 구성할 수 있어야 한다.
- **REV-005** 사용자는 사진과 설명을 첨부할 수 있어야 한다.
- **REV-006** 협찬, 초대, 할인, 직원 관계 등 이해관계를 공개할 수 있어야 한다.
- **REV-007** 리뷰 수정 이력을 내부적으로 보존하고 중요한 변경은 점수 재계산에 반영해야 한다.
- **REV-008** 동일 방문에 대한 중복 리뷰 게시를 제한해야 한다.
- **REV-009** 반복 방문 리뷰를 허용하되 음식점 점수에 과도한 영향이 없도록 계산해야 한다.
- **REV-010** 리뷰가 점수에 포함되는지, 제외되었다면 사용자에게 설명 가능한 상태를 가져야 한다.
- **REV-011** 리뷰 게시 전 금칙어뿐 아니라 개인정보, 위협, 광고, 무관한 콘텐츠 위험을 검사해야 한다.
- **REV-012** 사용자는 자신의 리뷰와 사진을 내려받거나 삭제할 수 있어야 한다.
- **REV-013** 리뷰 삭제가 집계 점수와 파생 데이터에 반영되어야 한다.

### 8.6 방문 인증

- **VER-001** 예약, 영수증, 매장 QR, 결제 연동, 위치 기반 인증을 독립적인 인증 수단으로 지원할 수 있어야 한다.
- **VER-002** 각 인증 수단의 신뢰 수준과 검증 시각을 저장해야 한다.
- **VER-003** 방문 인증 실패가 리뷰 게시 자체를 막지는 않되 점수 영향력에 반영할 수 있어야 한다.
- **VER-004** 영수증 원본과 위치 원본은 파생된 인증 결과와 분리해 저장해야 한다.
- **VER-005** 하나의 인증 증빙을 여러 계정이나 방문에 재사용하는 행위를 탐지해야 한다.
- **VER-006** 사용자는 인증 결과에 이의를 제기할 수 있어야 한다.

### 8.7 저장과 리스트

- **LST-001** 사용자는 음식점을 가고 싶은 곳과 다녀온 곳으로 저장할 수 있어야 한다.
- **LST-002** 사용자는 사용자 정의 리스트를 생성할 수 있어야 한다.
- **LST-003** 리스트는 공개, 링크 공개, 비공개 중 하나의 공개 범위를 가져야 한다.
- **LST-004** 리스트에 개인 메모를 저장할 수 있어야 하며 기본적으로 공개하지 않아야 한다.
- **LST-005** 리스트 작성자는 음식점 순서와 설명을 편집할 수 있어야 한다.
- **LST-006** 폐업하거나 이전한 음식점이 리스트에 포함되면 상태를 표시해야 한다.
- **LST-007** 사용자는 자신의 저장 데이터 전체를 내보낼 수 있어야 한다.

### 8.8 리뷰어와 소셜

- **SOC-001** 리뷰어 프로필은 리뷰 수, 방문 지역, 주요 장르, 평가 분포를 표시할 수 있어야 한다.
- **SOC-002** 전문성 수치는 최소 데이터 조건을 충족한 경우에만 공개해야 한다.
- **SOC-003** 사용자는 리뷰어를 팔로우하거나 차단할 수 있어야 한다.
- **SOC-004** 차단 관계는 리뷰 노출, 댓글, 알림에 일관되게 적용되어야 한다.
- **SOC-005** 팔로워 수가 음식점 평점 영향력으로 직접 변환되어서는 안 된다.
- **SOC-006** 리뷰어는 자신의 이해관계와 활동 정책을 공개할 수 있어야 한다.

### 8.9 랭킹과 어워드

- **RNK-001** 랭킹은 지역, 음식 장르, 가격대 및 기간을 기준으로 생성할 수 있어야 한다.
- **RNK-002** 데이터가 부족한 지역 또는 장르는 공식 랭킹 생성을 제한해야 한다.
- **RNK-003** 랭킹에는 기준일, 포함 조건, 제외 조건을 표시해야 한다.
- **RNK-004** 광고 구매 여부가 랭킹에 영향을 주어서는 안 된다.
- **RNK-005** 어워드 선정 당시 데이터와 결과를 스냅샷으로 보존해야 한다.
- **RNK-006** 폐업, 중대한 정책 위반 등 사유로 수상 상태를 변경할 수 있어야 하며 이력을 남겨야 한다.
- **RNK-007** 공개 점수, 인기, 개인 추천, 편집 선정, 광고는 서로 다른 label·방법·분석으로 구분해야 한다.
- **RNK-008** 어워드 후보와 심사 데이터에서 광고비, 구독 tier, 예약 계약 여부를 제외해야 한다.
- **RNK-009** 심사자는 점주·광고·고용·투자·무상 제공 등 이해충돌을 신고하고 필요한 경우 해당 후보 판단에서 제척되어야 한다.
- **RNK-010** 어워드는 지역·장르 coverage와 최소 evidence가 충족되지 않으면 발표를 보류할 수 있어야 한다.
- **RNK-011** 선정 program, 기준 시점, 대상 범위, 방법 요약, 연도, 정정·신고 경로를 공개해야 한다.
- **RNK-012** 점주가 선정 mark를 다른 지점·브랜드 전체·다른 연도로 확대 사용하지 못하도록 지점·기간·asset 범위의 라이선스를 관리해야 한다.

### 8.10 개인화

- **PER-001** 사용자의 저장, 검색, 평가, 팔로우 관계를 이용해 추천을 생성할 수 있어야 한다.
- **PER-002** 개인화 점수와 전체 공개 점수를 명확히 구분해야 한다.
- **PER-003** 사용자는 개인화 기능을 끄거나 추천 근거를 제한적으로 확인할 수 있어야 한다.
- **PER-004** 민감한 위치 또는 방문 패턴이 타인에게 추론되지 않도록 해야 한다.
- **PER-005** 신규 사용자에게는 지역, 장르, 가격 선호를 선택하는 콜드스타트 흐름을 제공할 수 있어야 한다.

### 8.11 예약

- **RSV-001** 사용자는 날짜, 시간, 인원으로 예약 가능한 음식점을 검색할 수 있어야 한다.
- **RSV-002** 좌석, 룸, 코스, 최소 주문, 이용 시간을 표시할 수 있어야 한다.
- **RSV-003** 예약은 요청, 확정, 변경 요청, 취소, 완료, 노쇼 상태를 가져야 한다.
- **RSV-004** 예약 확정 전에 취소 및 환불 정책에 동의해야 한다.
- **RSV-005** 동시 예약 경쟁 시 좌석 재고의 중복 판매를 방지해야 한다.
- **RSV-006** 점주와 사용자 양쪽에서 변경을 제안할 수 있어야 한다.
- **RSV-007** 예약금, 선결제, 취소 수수료와 환불 내역을 추적해야 한다.
- **RSV-008** 예약 완료는 방문 인증 신호로 사용할 수 있지만 실제 방문 여부를 별도로 판정해야 한다.
- **RSV-009** 외부 예약 서비스로 연결되는 경우 도락 내부 예약과 명확히 구분해야 한다.

### 8.12 알림

- **NTF-001** 예약 확정, 변경, 취소, 임박 알림은 거래 알림으로 분류해야 한다.
- **NTF-002** 리뷰 답변, 신고 결과, 정보 수정 결과를 관련 사용자에게 알려야 한다.
- **NTF-003** 마케팅 알림은 거래 알림과 별도로 동의를 관리해야 한다.
- **NTF-004** 사용자는 푸시, 이메일, 문자 등 채널별 설정을 변경할 수 있어야 한다.
- **NTF-005** 동일 사건에 대한 중복 알림을 억제해야 한다.

## 9. 점주 기능 요구사항

### 9.1 점주 인증과 권한

- **OWN-001** 사용자는 기존 음식점에 대한 관리 권한을 신청할 수 있어야 한다.
- **OWN-002** 사업자, 인허가, 전화, 이메일, 위임 서류 등 복수의 인증 방식을 지원해야 한다.
- **OWN-003** 한 음식점에 소유자, 관리자, 메뉴 편집자, 예약 담당자 역할을 부여할 수 있어야 한다.
- **OWN-004** 본사와 지점 권한을 분리해야 한다.
- **OWN-005** 구성원의 초대, 권한 변경, 제거 이력을 감사 로그에 남겨야 한다.
- **OWN-006** 소유권 분쟁 발생 시 임시 제한과 운영자 재검증이 가능해야 한다.

### 9.2 공식 정보 관리

- **OIN-001** 점주는 상호, 소개, 연락처, 영업시간, 편의시설을 수정할 수 있어야 한다.
- **OIN-002** 법적 또는 공공 원장과 충돌하는 핵심 정보는 즉시 반영하지 않고 검수할 수 있어야 한다.
- **OIN-003** 임시 휴무, 조기 마감, 재료 소진을 만료 시각과 함께 공지할 수 있어야 한다.
- **OIN-004** 점주 수정과 사용자 제보의 출처 우선순위가 필드별로 정의되어야 한다.
- **OIN-005** 점주는 공식 대표 사진과 로고를 설정할 수 있어야 한다.

### 9.3 메뉴 관리

- **MNU-001** 메뉴 그룹, 메뉴, 옵션, 가격, 설명, 알레르기 정보를 관리할 수 있어야 한다.
- **MNU-002** 기간 한정 및 일시 품절 상태를 설정할 수 있어야 한다.
- **MNU-003** 메뉴 변경 이력을 보존해야 한다.
- **MNU-004** 여러 지점에 공통 메뉴를 배포하고 지점별 가격을 재정의할 수 있어야 한다.
- **MNU-005** 메뉴판 이미지와 구조화된 메뉴 데이터의 출처를 구분해야 한다.

### 9.4 리뷰 대응

- **ORV-001** 인증된 점주는 매장 리뷰에 공식 답변을 작성할 수 있어야 한다.
- **ORV-002** 답변 수정 이력을 보존해야 한다.
- **ORV-003** 점주는 리뷰를 임의 삭제할 수 없으며 정책 사유로 신고할 수 있어야 한다.
- **ORV-004** 신고 상태와 결과를 확인하고 허용된 범위에서 이의를 제기할 수 있어야 한다.
- **ORV-005** 점주가 리뷰 작성자에게 보상이나 압력을 제공하는 행위를 금지하고 탐지 신호를 수집해야 한다.

### 9.5 예약 운영

- **ORS-001** 점주는 테이블, 룸, 좌석 조합, 회차, 이용 시간을 설정할 수 있어야 한다.
- **ORS-002** 전화, 현장, 외부 채널 예약을 수동 등록할 수 있어야 한다.
- **ORS-003** 예약 채널별 재고를 통합하거나 할당할 수 있어야 한다.
- **ORS-004** 휴무와 특별 영업일에 따라 예약 가능 시간을 생성해야 한다.
- **ORS-005** 예약 승인, 거절, 변경, 취소에 담당자와 사유를 기록해야 한다.
- **ORS-006** 노쇼 및 취소 수수료 정책을 사전에 설정할 수 있어야 한다.
- **ORS-007** 고객 메모 중 민감정보와 운영 메모의 접근 범위를 제한해야 한다.

### 9.6 분석과 광고

- **ANA-001** 점주는 검색 노출, 상세 조회, 저장, 전화, 길 찾기, 예약 전환을 확인할 수 있어야 한다.
- **ANA-002** 경쟁 음식점의 비공개 데이터나 개인 식별 데이터를 제공해서는 안 된다.
- **ADS-001** 유료 광고는 자연 검색 및 평점 랭킹과 별도의 노출 슬롯을 사용해야 한다.
- **ADS-002** 광고 성과와 비용을 점주가 확인할 수 있어야 한다.
- **ADS-003** 광고 계약 또는 미납 상태가 공개 평점에 영향을 주어서는 안 된다.
- **ADS-004** 모든 광고 항목은 카드·지도 핀·추천 모듈의 판단 지점에서 광고임을 명확히 표시해야 한다.
- **ADS-005** 광고 후보·랭킹·성과 이벤트와 자연 검색·추천 후보·랭킹·행동 이벤트를 분리해야 한다.
- **ADS-006** 폐업, 정책 정지, 만료된 혜택, 지점 권한 상실은 광고 노출 시점에 다시 검사해야 한다.
- **ADS-007** 광고 노출·클릭·전환은 중복과 무효 트래픽을 제거한 뒤에만 청구 가능 상태가 되어야 한다.
- **ADS-008** 점주는 invoice line과 광고·예약 사용 근거를 재현 가능한 범위에서 확인하고 이의를 제기할 수 있어야 한다.
- **ADS-009** 무료 점주 claim, 기본 정보 수정, 리뷰 신고·이의 제기를 구독 entitlement와 분리해야 한다.

## 10. 운영 기능 요구사항

### 10.1 음식점 데이터 운영

- **OPS-D-001** 신규, 수정, 폐업, 이전, 중복 후보를 별도 큐로 관리해야 한다.
- **OPS-D-002** 자동 규칙의 판정 근거와 신뢰도를 운영자가 확인할 수 있어야 한다.
- **OPS-D-003** 병합과 분리 작업은 되돌릴 수 있어야 한다.
- **OPS-D-004** 음식점 병합 시 리뷰, 사진, 저장, 예약 관계를 안전하게 이전해야 한다.
- **OPS-D-005** 모든 필드 변경에는 변경자, 출처, 시각, 이전 값, 새 값을 기록해야 한다.

### 10.2 콘텐츠 모더레이션

- **OPS-M-001** 신고 유형, 위험도, 법정 처리기한, 노출 규모에 따라 큐 우선순위를 정해야 한다.
- **OPS-M-002** 자동 탐지 결과만으로 중대한 계정 제재를 확정하지 않도록 검수 정책을 설정할 수 있어야 한다.
- **OPS-M-003** 조치에는 표준 사유 코드를 사용해야 한다.
- **OPS-M-004** 블라인드, 삭제, 검색 제한, 점수 제외, 계정 제한을 독립적으로 적용할 수 있어야 한다.
- **OPS-M-005** 이의 제기 담당자는 가능한 경우 최초 결정자와 분리해야 한다.
- **OPS-M-006** 법적 보존 대상 증빙과 일반 운영 데이터를 구분해야 한다.

### 10.3 권한과 감사

- **OPS-A-001** 운영자 권한은 최소 권한 원칙과 역할 기반 접근제어를 적용해야 한다.
- **OPS-A-002** 민감정보 열람에는 사유 입력과 감사 로그를 요구해야 한다.
- **OPS-A-003** 대량 내보내기, 점수 수동 변경, 계정 복구 등 고위험 작업은 추가 승인을 요구할 수 있어야 한다.
- **OPS-A-004** 감사 로그는 일반 운영자가 수정하거나 삭제할 수 없어야 한다.

## 11. 공통 품질 요구사항

### 11.1 접근성

- **QLT-A-001** 핵심 소비자 웹은 WCAG 2.2 AA 수준을 목표로 한다.
- **QLT-A-002** 모바일 앱은 운영체제의 글자 크기, 화면 읽기, 대비 설정을 지원해야 한다.
- **QLT-A-003** 색상만으로 평점, 영업 상태, 경고를 구분하지 않아야 한다.
- **QLT-A-004** 지도 외에 동일 정보를 탐색할 수 있는 목록 수단을 제공해야 한다.

### 11.2 국제화

- **QLT-I-001** UI 문구와 음식점 콘텐츠를 분리해 다국어를 지원해야 한다.
- **QLT-I-002** 원문, 점주 제공 번역, 자동 번역을 구분해 저장해야 한다.
- **QLT-I-003** 통화, 시간대, 전화번호, 주소 표기 형식을 로케일에 맞게 표시해야 한다.
- **QLT-I-004** 고유한 음식명은 번역명과 원어명을 함께 제공할 수 있어야 한다.

### 11.3 성능과 가용성

- **QLT-P-001** 음식점 상세과 검색은 모바일 네트워크에서도 핵심 콘텐츠가 빠르게 표시되어야 한다.
- **QLT-P-002** 사진 장애가 검색과 예약 같은 핵심 기능을 차단해서는 안 된다.
- **QLT-P-003** 예약 생성과 결제 콜백은 멱등성을 보장해야 한다.
- **QLT-P-004** 평점 재계산 중에도 이전 공개 점수를 안정적으로 제공해야 한다.
- **QLT-P-005** 외부 지도 또는 인증 공급자 장애 시 기능 저하 상태를 명확히 처리해야 한다.

### 11.4 보안과 개인정보

- **QLT-S-001** 개인정보와 공개 프로필 데이터를 논리적으로 구분해야 한다.
- **QLT-S-002** 영수증, 결제, 위치 원본은 암호화하고 접근을 제한해야 한다.
- **QLT-S-003** 사용자 세션과 점주 세션의 위험도를 구분할 수 있어야 한다.
- **QLT-S-004** 계정 탈취가 점주 정보 및 예약 데이터 변경으로 이어지지 않도록 추가 인증을 적용해야 한다.
- **QLT-S-005** 보존기간이 지난 개인정보와 인증 원본을 자동 파기해야 한다.

## 12. 수익 모델 원칙

도락의 수익은 평가 신뢰도를 훼손하지 않는 영역에서 발생해야 한다.

- 점주용 고급 매장 관리 기능 구독
- 명확히 표시된 검색 및 디스플레이 광고
- 예약 성사 수수료
- 예약금 및 노쇼 관리 부가 서비스
- 소비자 프리미엄 검색 및 개인화 기능
- 익명화된 시장 통계와 기업용 도구

다음 상품은 허용하지 않는다.

- 평점 구매
- 부정 리뷰 삭제 상품
- 광고 계약을 조건으로 한 랭킹 상승
- 긍정 리뷰 작성을 조건으로 한 사용자 보상
- 개인을 재식별할 수 있는 방문 데이터 판매

## 13. 단계별 공개 범위

단계 구분은 최종 제품 범위를 축소하기 위한 것이 아니라 데이터와 운영 품질을 안정적으로 확보하기 위한 출시 순서다.

### Foundation

- 전국 음식점 원장
- 웹 검색과 음식점 상세
- 지도 탐색
- 관리자 데이터 검수
- 점주 인증과 공식 정보 관리

### Trust

- 계정과 프로필
- 리뷰와 사진
- 방문 인증
- 평점 엔진
- 리뷰 신고와 이의 제기
- 지역 및 장르 랭킹

### Network

- 리뷰어 팔로우
- 리스트와 피드
- 개인화 추천
- 에디터 콘텐츠
- 어워드
- 다국어 탐색

### Transaction

- 예약과 웨이팅
- 예약금 및 취소 수수료
- 점주 예약대장
- 고객 알림
- 예약 기반 방문 인증

### Platform

- 프랜차이즈와 그룹 관리
- 외부 예약 및 POS 연동
- 기업용 분석
- 공개 또는 파트너 API
- 고급 어뷰징 탐지

## 14. 핵심 지표

### 14.1 신뢰

- 방문 인증 리뷰 비율
- 점수 계산에 포함되는 리뷰 비율
- 조작 의심 리뷰의 사전 차단율과 오탐률
- 리뷰 신고 인용률
- 이의 제기로 결정이 변경된 비율
- 평점에 대한 사용자 신뢰도 조사

### 14.2 데이터 품질

- 영업 중 음식점의 핵심 정보 완성도
- 폐업 및 이전 반영 소요 시간
- 중복 음식점 비율
- 영업시간 최신 확인 비율
- 사용자 제보 처리 시간

### 14.3 탐색 가치

- 검색 결과에서 상세 페이지 진입률
- 상세 페이지에서 저장, 길 찾기, 전화, 예약으로의 전환율
- 검색 결과 없음 비율
- 저장한 음식점의 실제 방문 전환율
- 지역 및 장르별 유효 리뷰 밀도

### 14.4 네트워크

- 월간 리뷰 작성자 수
- 핵심 리뷰어 유지율
- 팔로우 후 콘텐츠 소비율
- 공개 리스트 저장 및 공유율

### 14.5 거래와 점주

- 인증 점주 매장 수
- 예약 가능 매장 수
- 예약 성사율과 노쇼율
- 점주 정보 수정 처리율
- 점주 유료 전환 및 유지율

## 15. 제품 의사결정 규칙

기능 우선순위는 다음 질문으로 판단한다.

1. 음식점 선택의 신뢰도를 높이는가?
2. 음식점 데이터의 정확도와 최신성을 높이는가?
3. 양질의 리뷰가 지속해서 쌓이게 하는가?
4. 점수와 광고의 독립성을 유지하는가?
5. 운영자가 정책에 따라 확장 가능하게 처리할 수 있는가?
6. 사용자와 점주의 권리를 함께 보호하는가?

위 질문에 대부분 답하지 못하는 기능은 핵심 로드맵보다 뒤로 배치한다.
