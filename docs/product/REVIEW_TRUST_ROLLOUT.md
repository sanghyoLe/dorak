# 리뷰 신뢰 도입 순서

도락의 핵심은 식당 정보의 양보다 믿고 읽을 수 있는 식사 경험이다.
이 문서는 현재 구현과 이후 작업을 구분한다. 평점·운영 상세 문서의 장기 설계가 모두 구현된 것은 아니다.

## 이번 구현

- 새 리뷰는 이 지점의 음식을 직접 먹었다는 확인과 협찬·리뷰 대가·식당 이해관계 없음 확인을 모두 요구한다. 매장 식사·포장·배달 중 이용 방식도 필수다. API도 누락·잘못된 값을 거부한다.
- 이해관계 확인은 작성자의 진술이다. 영수증 확인이나 본인 인증 배지를 부여하지 않는다.
- 기존 리뷰의 새 필드는 NULL로 유지하고 ‘이해관계 미확인’으로 표시한다. 과거 데이터를 임의로 인증하지 않는다.
- 이메일 확인, 이용 방식·이용일 자기입력, 이해관계 자기 확인을 별도로 표시한다. 이용일 미입력을 작성일로 대체하지 않는다.
- 상세에서 매장 식사·포장·배달별 공개 리뷰 수와 단순 평균을 보여주고 URL 필터로 해당 리뷰만 읽을 수 있다. 기존 리뷰는 `usage_type = NULL`로 남겨 ‘이용 방식 미확인’으로 따로 집계한다. 0건인 방식은 0점이 아닌 ‘평가 전’으로 표시한다.
- 목록·상세 상단의 기존 전체 평균과 검색 정렬은 유지한다. 방식별 대표 점수로 교체한 것은 아니다. 계정당 지점별 1건 제한도 유지한다.
- 리뷰 하단의 앱 내 신고 폼에서 정책 유형과 구체적인 문제 부분을 접수할 수 있다. 신고 본문은 공개하지 않고 운영 대기열에만 전달하며, 운영자는 처리 사유와 함께 처리 완료 또는 기각을 기록한다. 신고 처리와 리뷰 공개 숨김은 분리한다.
- 같은 로그인 계정의 동일 리뷰·동일 사유 중복 신고는 막는다. 로그인하지 않은 신고도 접수하되, 현재는 신고자에게 사건 상태를 제공하지 않는다.
- DB/API의 기존 `visitedOn`, `visitAttested` 이름은 호환성을 위해 유지하지만 새 리뷰에서는 이용일과 직접 섭취 확인을 뜻한다. `usageType`은 `dine_in`, `takeout`, `delivery`만 받는다.
- 현재 점수는 숨김 리뷰를 제외한 공개 리뷰의 단순 평균이며, 이해관계 미확인인 기존 리뷰도 포함한다. 신뢰 가중 점수는 아직 없다.
- 협찬 리뷰를 공개하되 점수에서 제외하는 장기안은 이번에 도입하지 않는다. 현재는 기존 공개 원칙대로 등록을 받지 않는다.

## 다음 구현: 비공개 이용 증빙

증빙 제출 화면만 먼저 만들지 않는다. 아래 경로 전체가 작동한 뒤 공개한다.

1. 리뷰 작성자만 영수증·예약·배달 주문 내역을 제출할 수 있게 한다. 공개 사진과 별도 비공개 저장소를 사용한다. 배달 주문의 정확한 지점과 주문 완료 여부를 확인하며 주문만으로 실제 섭취를 보장하지 않는다.
2. 업로드 전에 이름·전화번호·결제번호 등 불필요한 정보를 가리도록 안내한다. 파일 크기·형식·실제 내용 검사와 접근 권한 검사를 넣는다.
3. 운영자는 지점·이용일·이용 방식과 증빙의 일치를 확인한다. 예약만으로 실제 식사를 보장하지 않으므로 ‘예약 내역 확인’과 ‘영수증 확인’을 구분한다. 협찬 여부까지 인증하지 않는다.
4. 제출 → 검토 중 → 확인/반려 → 취소 상태와 처리자·사유·시각을 감사 기록으로 남긴다. 작성자는 반려 이유를 확인하고 재제출할 수 있어야 한다.
5. 확인 상태는 운영자 서버 경로에서만 변경한다. 공개 API나 작성자 입력으로 배지를 얻지 못하게 테스트한다.
6. 보관 기간·삭제 시점·계정 탈퇴 처리·백업 삭제 범위를 정하고 개인정보 안내에 반영한다. 저장소와 운영 검토 담당자가 준비되기 전에는 수집하지 않는다.

완료 기준: 다른 계정의 증빙 접근 차단, 공개 응답에 원본 URL 미포함, 확인 취소 시 표시 복구, 삭제와 감사 기록 테스트까지 통과.

## 초기 리뷰 모집 실험

아래 숫자는 실적이 아니라 작은 시작을 위한 제안이다. 실제 초대는 아직 보내지 않았다.

- 한 동네의 식당 10곳에서 시작하고, 최근 직접 식사한 사람 10명에게 자발적인 참여를 요청한다.
- 좋은 점과 아쉬운 점을 모두 요청한다. 고평점이나 리뷰 개수에 따른 금전·식사 보상을 제공하지 않는다.
- 기존 서비스 리뷰를 복사·수집하지 않는다. 참여자가 자신의 경험을 직접 새로 작성한다.
- 먹은 메뉴, 방문 시점, 가격 대비 경험, 재방문 판단과 이유를 안내한다. 평점이나 결론을 대신 써주지 않는다.
- 2주 뒤 식당별 독립 작성자 수, 구체적인 식사 경험이 담긴 리뷰 비율, 신고와 처리 결과, 리뷰를 읽고 방문 결정에 도움이 됐다는 피드백을 확인한다.
- 평균 점수 상승이나 긍정 리뷰 비율을 성공 지표로 쓰지 않는다. 운영자 지인 모집에 따른 편향도 기록한다.

초대 문안: “최근 직접 다녀온 식당의 식사 경험을 도락에 남겨주실 수 있나요? 먹은 메뉴와 좋았던 점, 아쉬웠던 점을 솔직하게 적어주세요. 협찬이나 리뷰 대가를 받은 방문, 관계가 있는 식당은 제외합니다. 참여 보상이나 높은 평점 요청은 없습니다.”

## 이후 평점 변경 조건

리뷰가 충분히 쌓이기 전에는 복잡한 신뢰 점수를 만들지 않는다. 표본 부족 표시·평점 공개 최소 건수·이해관계 미확인 리뷰의 처리 방식을 먼저 결정한다. 산식이 바뀌면 목록·검색 정렬·상세·운영 화면을 함께 바꾸고 기존 리뷰 영향을 검증한다.

## 이용 방식 회귀 검사

`DATABASE_URL= DORAK_DEMO_AUTH=true pnpm --filter @dorak/web exec next dev -p 3000`으로 새 메모리 서버를 시작한 뒤 `node scripts/review-usage-smoke.mjs`를 실행한다. 세 방식의 필수 입력·실제 등록·초기화·평점·필터·모바일 폭을 검사한다. 테스트 리뷰가 남으므로 재실행할 때 메모리 서버를 다시 시작한다. 스크립트는 Postgres 환경에서 실행을 거부한다.
